# Архивация вместо удаления

Сущность нельзя тихо удалить, если на неё уже кто-то ссылается — иначе внешний ключ либо упадёт с ошибкой БД, либо (что хуже) молча обнулится.

## Единая точка: `src/lib/archive.ts::archiveOrDelete(type, id, orgId)`

1. Проверяет ссылки на сущность (`checkReferences`) — свои правила на каждый тип
2. Если ссылок нет — обычный `delete`
3. Если есть — переводит в `status: ARCHIVED` и возвращает человекочитаемую причину

Типы: `employee`, `client`, `catalogItem`, `vaultServiceEntry`, `store`. Каждый `deleteX` Server Action обязан идти через эту функцию, а не звать `prisma.x.delete()` напрямую.

## Находка, которая всё запустила (см. [[SetNull против Restrict]])

У Prisma по умолчанию для необязательных внешних ключей — `onDelete: SetNull`, не `Restrict`. Обнаружено на `Order.clientId`: удаление клиента с заказами тихо обнуляло ссылку в заказе, не блокируя удаление. Отсюда — везде, где это важно, теперь либо явный `onDelete: Restrict` в схеме, либо явная проверка в action перед записью (когда `SetNull` осознанно оставлен ради других причин — см. `Payment.orderId`, `Order.contractId`).

## Сущности, которые НЕ архивируются, а просто блокируют удаление

Справочники без собственной бизнес-истории — `Unit`, `CatalogGroup`, `Characteristic`, `SalesChannel`, `Contract` — не архивируются, а просто отказывают в удалении с сообщением "используется в N...". Смысла архивировать справочник нет — он не incident, не документ.

## Складские движения и заказы — вообще неизменяемы

`StockMovement` и (де-факто) уже отгруженные/принятые части `Order`/`PurchaseOrder` никогда не редактируются и не удаляются — ошибка исправляется новым корректирующим документом (см. [[Склад]], [[Заказы и закупки]]). Это не архивация, а более строгий инвариант: история движений в принципе неприкосновенна, как бухгалтерский леджер.
