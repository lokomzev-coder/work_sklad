# Ролевая модель

Три роли: `ADMIN`, `MANAGER`, `EMPLOYEE`. Определены в `src/lib/permissions.ts`.

## Модель прав

`Access = "none" | "read" | "edit" | "full"`, ранжированы численно. `can(role, resource, need)` / `assertPermission(role, resource, need)` — вторая бросает исключение, если прав не хватает (используется в начале каждого Server Action).

Ресурсы: `vault`, `employees`, `clients`, `catalog`, `orders`, `membership`, `warehouse`.

## Асимметрия ролей (нарочно, не забыть при новых фичах)

- `EMPLOYEE`: `vault: none` (совсем не видит пароли — вплоть до `notFound()` при прямом заходе по URL, не только скрытие пункта меню), `catalog: read` (не может создавать/редактировать позиции), `warehouse: read` (не может проводить складские движения — это на менеджерах/админах), `orders: edit` (может создавать заказы, отгрузка/приёмка — уже `warehouse`, отдельное право)
- `MANAGER`: почти `full` везде, кроме `employees: edit` (не `full`) и `membership: read`
- `ADMIN`: `full` везде

## Двойная проверка — правило, не опция

Проверка прав **всегда** на двух уровнях:
1. В самом Server Action (`assertPermission`) — потому что Actions доступны напрямую по HTTP, скрытая кнопка в UI не защита
2. В UI — скрытие пунктов меню/кнопок для тех, у кого `can()` возвращает false — только для чистоты интерфейса, не как единственная защита

См. [[Мультитенантность]] для организационной изоляции (отдельная ось от ролей).
