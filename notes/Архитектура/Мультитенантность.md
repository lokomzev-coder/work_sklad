# Мультитенантность

SaaS-модель: одна инсталляция — много организаций (`Organization`). Маршруты — `/[org]/...`, где `org` — slug организации.

## Точка входа

`src/lib/tenant.ts::getOrgContext(orgSlug)` — единственная точка проверки членства:
- редирект на `/login`, если не авторизован
- редирект на `/org-select`, если пользователь не состоит в этой организации
- возвращает `{ orgId, orgSlug, orgName, role, userId }`

Каждая серверная страница и каждый Server Action вызывает `getOrgContext` (или получает `ctx.orgId` через него) — Server Actions в Next.js доступны напрямую по HTTP (POST), поэтому обязаны сами проверять авторизацию, а не полагаться на скрытость в UI.

## Изоляция данных

Каждая org-специфичная модель имеет `orgId` и составные проверки `where: { id, orgId }` — без этого одна организация могла бы прочитать/изменить данные другой по прямому ID. Особенно критично для [[Пароли (vault)|vault]], где DEK (data-encryption-key) свой на организацию — DEK организации B физически не может расшифровать секрет организации A.

## Сессия

NextAuth v5 (beta), JWT-стратегия. `session.memberships[]` — все организации пользователя, заполняется в JWT-колбэке (`src/lib/auth.ts`) без похода в БД на каждый запрос. Используется в [[Ролевая модель|проверке прав]] и в `OrgSwitcher` (переключатель организации в сайдбаре).

## Кросс-организационная инъекция — повторяющийся класс бага

Любое поле формы, которое передаёт ID сущности (unitId, groupId, parentId группы, variantId, contractId...), нужно **явно проверять на принадлежность текущей organzId** перед записью — иначе злонамеренная форма может привязать сущность к чужой организации. Паттерн: `assertRefsBelongToOrg`/`assertParentBelongsToOrg` и подобные — искать по `actions/*.ts`.
