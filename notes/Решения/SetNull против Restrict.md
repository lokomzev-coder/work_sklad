# SetNull против Restrict

Самый частый класс найденных багов в проекте — вылезал минимум 3 раза, стоит проверять при каждой новой опциональной связи.

## Суть проблемы

У Prisma по умолчанию `onDelete` для **необязательного** внешнего ключа — `SetNull`, не `Restrict`. Значит `prisma.x.delete()` на сущность, на которую кто-то ссылается через опциональный FK, **не падает и не блокируется** — просто тихо обнуляет ссылку у всех, кто на неё указывал.

## Где нашли впервые

`Order.clientId` — удаление клиента с заказами молча обнуляло `clientId` в заказе вместо ошибки. Отсюда родился весь паттерн [[Архивация вместо удаления]].

## Где нашли снова

`Order.contractId`/`PurchaseOrder.contractId` — тот же класс бага, подтверждён отдельным тестовым скриптом при реализации договоров: удаление `Contract` с привязанными заказами прошло бы тихо, если бы не явная проверка в `actions/contracts.ts::deleteContract`.

## Два способа защититься — оба легитимны, выбор осознанный

1. **Явный `onDelete: Restrict` в схеме** — когда сущность-историческая запись, которую нельзя оставлять "осиротевшей" (напр. `StockMovementLine.catalogItemId`, `CatalogGroup.parent`)
2. **`SetNull` в схеме + явная проверка в action** — когда сущность-ссылка (не сам заказ) действительно не должна пропадать вместе с удалением связанного справочника (напр. `Payment.orderId` — платёж должен пережить удаление заказа; `Order.contractId` — заказ не должен исчезнуть вместе с договором)

**Правило**: если выбран вариант 2 (`SetNull`), проверка в action **обязательна**, иначе это не "мягкая деградация", а тихая порча данных без всякого предупреждения пользователю.

См. также [[Мультитенантность#Кросс-организационная инъекция]] — родственный класс "забыли проверить перед записью".
