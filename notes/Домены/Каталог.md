# Каталог

`CatalogItem` — единая таблица с discriminator `type: PRODUCT | SERVICE | BUNDLE`, а не три отдельные таблицы (см. [[Леджер вместо отдельных документов]] — тот же принцип: не плодить модели там, где хватает поля-дискриминатора).

## Комплекты (Bundle)

`CatalogItemComponent` — join-таблица (bundleId → componentId, quantity). Вложенные комплекты запрещены **на уровне action** (`actions/catalog-bundles.ts`), не в схеме — Prisma не может это выразить декларативно. UI: `BundleComponentsEditor` на странице товара, показывается только для `type: BUNDLE`.

## Модификации (Variant)

`Characteristic` (справочник, напр. "Размер") + `CatalogItemVariant` (своя цена-override/артикул/штрихкод) + `CatalogItemVariantValue`. Только для `type: PRODUCT`.

**Важное упрощение**: у варианта НЕТ собственного остатка — [[Склад|склад]] считает только по базовому `CatalogItem`. `OrderLineItem.variantId` позволяет заказать конкретную модификацию (см. [[Прайсинг — снапшот на момент документа]]), но отгрузка/приёмка всё ещё работают на уровне базового товара.

## Группы и единицы

`CatalogGroup` — self-relation `parentId`, дерево с защитой от циклов (`isDescendant` при смене родителя). `Unit` — простой справочник (название + сокращение). Оба не архивируются, просто блокируют удаление, если используются (см. [[Архивация вместо удаления]]).

## Складской учёт

Только `type: PRODUCT` участвует в [[Склад|складском леджере]] — услуга не физический товар, остаток комплекта не отслеживается отдельно (считался бы из остатков компонентов, если бы был нужен отчёт).

Связанное: [[Заказы и закупки]] (откуда берётся `unitPriceSnapshot`), [[Отчёты]] (обороты по товару).
