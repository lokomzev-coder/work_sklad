## 4. Разработка плана

Для проектирования архитектуры был запущен `Plan`-агент с подробным техническим заданием, учитывающим все согласованные решения. Агент вернул детальный план, включающий:

- Структуру репозитория (Next.js App Router, `src/app`, `src/actions`, `src/lib`, `src/components`)
- Модель мульти-тенантности через `/[org]/...` маршруты и `lib/tenant.ts::getOrgContext()`
- Обоснование выбора **Server Actions** как основного механизма мутаций (вместо REST API)
- Эскиз схемы Prisma: `User`, `Organization`, `Membership`, `Employee`, `Client`, `CatalogItem`, `Order`/`OrderLineItem`, `VaultServiceEntry`, `EmployeeVaultAccess`, `Tag`/`TagOnVaultEntry`, `VaultAccessLog`
- Логику «архив вместо удаления» (`archiveOrDelete`) для сущностей, на которые есть ссылки
- Модель ролей и прав (`lib/permissions.ts`)
- Модуль пароль-менеджера: двухуровневое шифрование (мастер-ключ приложения оборачивает per-org DEK), AES-256-GCM, авто-теги по доступу сотрудников, аудит-лог раскрытия секретов
- Выбор **shadcn/ui** поверх Tailwind как системы компонентов
- 9 фаз реализации (Phase 0 → Phase 8), от каркаса проекта до полировки UI
- Подход к верификации: ручной прогон golden path на каждой фазе + точечные автотесты для самой рискованной логики (архивация, шифрование, изоляция тенантов, авто-теги)

Полный план был сохранён в файл плана и одобрен пользователем через `ExitPlanMode`.

### Блокер: пропало интернет-соединение

При попытке выполнить `npx prisma -v` (для проверки версии и загрузки бинарников движка Prisma) команда зависла и завершилась с ошибкой:

```
Error: request to https://binaries.prisma.sh/.../schema-engine.exe.gz.sha256 failed,
reason: getaddrinfo ENOTFOUND binaries.prisma.sh
```

Дальнейшая диагностика показала, что сеть недоступна полностью:
- `node -e "fetch(...)"` к npm registry, GitHub, GitHub Objects — везде `fetch failed`.
- `curl` к `registry.npmjs.org` — таймаут DNS-резолвинга.
- `npm ping` — `ENOTFOUND registry.npmjs.org`.
- `nslookup registry.npmjs.org` — DNS-сервер `1.1.1.1` не отвечает вообще ни на один запрос.
- Проверка `netsh winhttp show proxy` показала прямое подключение без прокси — то есть дело не в прокси-настройках, а в реальном отсутствии соединения на уровне сети/DNS.
- Повтор теста с `dangerouslyDisableSandbox: true` дал тот же результат — значит, это не ограничение песочницы инструмента, а реальный обрыв сети на машине.

## 7. Настройка автоматизации Claude Code (по просьбе пользователя)

Пользователь попросил: (1) разрешить Claude самостоятельно запускать команды разработки (npm/npx/git/docker) без подтверждения на каждый шаг, и (2) настроить автоматическое обновление `chat_history.md` после каждой остановки.

Реализовано в `.claude/settings.local.json` (личный, не коммитится — добавлен в `.gitignore`):

- **Permissions.allow**: `Bash(npm *)`, `Bash(npx *)`, `Bash(node --version|-v)`, безопасные git-команды (`status`, `diff`, `log`, `show`, `add`, `commit` — без `push`/`reset --hard`/force), `Bash(docker compose *)`, `Bash(docker-compose *)`, `Bash(docker --version)`. Деструктивные операции сознательно не добавлены в allow-list — для них по-прежнему будет запрос подтверждения.
- **Hooks.Stop**: bash-команда, которая при каждой остановке ищет файлы новее `chat_history.md` (исключая `.git`, `node_modules`, `.next`). Если такие есть — возвращает `{"decision":"block","reason":"..."}`, что заставляет Claude дописать сводку в `chat_history.md` перед завершением ответа. Если новых изменений нет — `{"continue":true}`. Команда протестирована в обеих ветках (block/continue) через прямой запуск в шелле.

## 9. Важная находка: баг `prisma dev` + `template1`, переход на `db push`

При попытке создать вторую миграцию (`add_employee`) `prisma migrate dev` стабильно падал на этапе применения к shadow-базе с ошибкой `type "Role" already exists`, хотя shadow-база была пуста. Причина: изначальная строка подключения (напечатанная самим `prisma dev --detach`) указывала на **`template1`** — служебную базу PostgreSQL, которая по умолчанию используется как шаблон для ЛЮБОЙ новой базы (`CREATE DATABASE` копирует её содержимое). Так как наши таблицы физически лежали в `template1`, каждая новая shadow-база (и любая другая новая база) автоматически наследовала уже существующие объекты — отсюда конфликт.

Что сделано:
- `template1` полностью очищена (DROP TABLE/TYPE) и оставлена пустой — as it should be.
- Заведена отдельная выделенная база **`easywork`**, на неё указывает `DATABASE_URL` в `.env`/`.env.example` (см. предупреждающий комментарий там же).
- Несмотря на очистку, `prisma migrate dev` продолжал давать сбои даже на новых именованных инстансах `prisma dev` (похоже на баг/квирк персистентности этой сравнительно новой фичи Prisma 7 — данные "просачивались" между инстансами непонятным образом). После нескольких попыток пересоздания решено **временно перейти на `npx prisma db push`** вместо `prisma migrate dev` — `db push` не использует shadow-базу вообще и сработал сразу и чисто.
- Папка `prisma/migrations/` удалена (она не соответствовала реальному состоянию БД при работе через `db push`). Как только будет доступен стабильный Postgres (Docker или собственная миграция `prisma dev` без этого бага), нужно будет сгенерировать нормальную историю миграций заново через `prisma migrate dev --name init`.
- **Практическое следствие**: пока используем `npx prisma db push` после каждого изменения `prisma/schema.prisma`, а не `migrate dev`. Это ок для сольной разработки на раннем этапе, но перед продакшеном/CI нужно будет вернуться к миграциям с историей.

## 14. Исправления по фидбеку: шрифт и рантайм-ошибка Prisma

Синглтон `PrismaClient` в `src/lib/prisma.ts` намеренно кэшируется в `globalThis` между Fast Refresh перезагрузками (чтобы не плодить соединения при hot reload) — но это же означает, что после `prisma generate` с новой моделью старый долгоживущий процесс dev-сервера продолжает держать в памяти старый инстанс клиента без `.employee`. Исправлено перезапуском dev-сервера (`taskkill` старого PID + свежий `npm run dev` в фоне) после свежего `prisma generate`. **Важно на будущее**: после любого изменения `prisma/schema.prisma` + `db push`/`generate` — dev-сервер нужно перезапускать, иначе будет та же ошибка.

Это именно та проблема, для решения которой в плане и была заложена Phase 6 — реализовали её сразу, не откладывая, раз баг уже реально нашёлся.

## 21. Phase 7 — Модуль паролей (vault) реализован с упором на безопасность

Пользователь попросил сделать всё "качественно и безопасно" — это самый чувствительный модуль проекта (шифрование секретов), подошёл к нему с особым вниманием к проверке.

### Схема и шифрование

- `prisma/schema.prisma`: `VaultServiceEntry` (`ciphertext/nonce/authTag` — отдельные `Bytes`-поля, `status`/`archivedAt` как у других архивируемых сущностей), `EmployeeVaultAccess` (join `Employee↔VaultServiceEntry`, `grantedById`), `Tag`/`TagOnVaultEntry` (`kind: MANUAL | EMPLOYEE_ACCESS`), `VaultAccessLog` (аудит раскрытия секрета).
- `src/lib/crypto.ts` — AES-256-GCM. Двухуровневая схема ключей: мастер-ключ приложения (`ENCRYPTION_MASTER_KEY` из `.env`, 32 байта) оборачивает случайный per-org DEK (`Organization.encDekWrapped/encDekNonce`); каждый секрет шифруется собственным случайным nonce на DEK организации. `authTag` проверяется при расшифровке — при подмене шифротекста/тега/использовании неверного ключа выбрасывается исключение (не проглатывается молча).
- `src/lib/org-dek.ts` — `getOrgDek(orgId)` с ленивым бэкфиллом: если у организации ещё нет DEK (создана до Phase 7), он генерируется и сохраняется атомарно при первом обращении к vault.
- `registerAction` (регистрация) теперь сразу создаёт DEK для новой организации — бэкфилл нужен только для организаций, заведённых раньше.
- Технический нюанс: новые версии `@types/node`/TypeScript различают `Buffer<ArrayBufferLike>` и `Uint8Array<ArrayBuffer>`, а сгенерированный Prisma-клиент требует именно второе для `Bytes`-полей — пришлось явно материализовать чистые `Uint8Array<ArrayBuffer>` на границе с Prisma (`Uint8Array.from()`), иначе сборка не проходила.

### Бизнес-логика

- `src/actions/vault.ts` — CRUD записи (секрет write-only: на редактировании поле всегда пустое, если оставить пустым — пароль не меняется), `grantVaultAccess`/`revokeVaultAccess` (авто-тег на сотрудника создаётся лениво через `upsert`, переиспользуется между записями, при отзыве удаляется только связь тег↔запись, а не сам тег), `revealVaultSecret` — отдельное действие от обычного открытия карточки, пишет строку в `VaultAccessLog`.
- `src/actions/employees.ts::updateEmployee` — при переименовании сотрудника синхронизирует имя его авто-тега (с защитой от коллизии уникальных имён через try/catch, чтобы не сломать сохранение профиля).
- `lib/archive.ts` расширен: `vaultServiceEntry` архивируется вместо удаления, если у записи есть хоть один выданный доступ; `employee` теперь также проверяется на `EmployeeVaultAccess`, а не только на заказы.

### UI и контроль доступа

- Страницы `/[org]/vault`, `/new`, `/[id]` (карточка: раскрытие пароля, управление доступом сотрудников через комбобокс, недавние просмотры).
- **Проверка доступа — на уровне маршрута, не только в UI**: список и карточка вызывают `can(ctx.role, "vault", "read")` и делают `notFound()` для роли EMPLOYEE (а не просто прячут пункт меню — тот факт, что ссылка скрыта в сайдбаре, не мешает зайти по прямому URL).
- Подключен `<Toaster />` (sonner) в корневой layout — использован для обратной связи при архивации/удалении.

### Проверка (расширенный тест на 21 пункт, все прошли)

Написан временный скрипт, покрывающий именно то, что чаще всего ломается в подобных системах:
- round-trip шифрования; два шифрования одного текста дают разные nonce/шифротекст; порча шифротекста/authTag/использование чужого ключа — исключение;
- wrap/unwrap DEK корректен; **два DEK разных организаций различны, и DEK организации B не может расшифровать секрет организации A** (проверка реальной мультитенантной изоляции секретов, не только данных);
- ленивый бэкфилл DEK для "старой" организации и его персистентность;
- повторная выдача доступа одному сотруднику на разные записи переиспользует один и тот же тег (не плодит дубликаты); отзыв с одной записи не трогает тег, если он ещё используется на другой;
- `archiveOrDelete`: запись без выданных доступов — удаляется; с выданным доступом — архивируется; сотрудник с доступом к vault — архивируется, а не удаляется;
- запись в `VaultAccessLog` создаётся.

Отдельно проверено: `can()`/`assertPermission()` действительно блокируют роль EMPLOYEE на уровне `vault`, HTTP-редиректы `/acme/vault`, `/acme/vault/new` для неавторизованных работают. `npm run build` проходит.
