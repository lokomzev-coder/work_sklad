## 4. Разработка плана

Для проектирования архитектуры был запущен `Plan`-агент с подробным техническим заданием, учитывающим все согласованные решения. Агент вернул детальный план, включающий:

- Структуру репозитория (Next.js App Router, `src/app`, `src/actions`, `src/lib`, `src/components`)
- Модель мульти-тенантности через `/[org]/...` маршруты и `lib/tenant.ts::getOrgContext()`
- Обоснование выбора **Server Actions** как основного механизма мутаций (вместо REST API)
- Эскиз схемы Prisma: `User`, `Organization`, `Membership`, `Employee`, `Client`, `CatalogItem`, `Order`/`OrderLineItem`, `VaultServiceEntry`, `EmployeeVaultAccess`, `Tag`/`TagOnVaultEntry`, `VaultAccessLog`
- Логику «архив вместо удаления» (`archiveOrDelete`) для сущностей, на которые есть ссылки
- Модель ролей и прав (`lib/permissions.ts`)
- Модуль пароль-менеджера: двухуровневое шифрование (мастер-ключ приложения оборачивает per-org DEK), AES-256-GCM, авто-теги по доступу сотрудников, аудит-лог раскрытия секретов
- Выбор **shadcn/ui** поверх Tailwind как системы компонентов
- 9 фаз реализации (Phase 0 → Phase 8), от каркаса проекта до полировки UI
- Подход к верификации: ручной прогон golden path на каждой фазе + точечные автотесты для самой рискованной логики (архивация, шифрование, изоляция тенантов, авто-теги)

Полный план был сохранён в файл плана и одобрен пользователем через `ExitPlanMode`.

### Блокер: пропало интернет-соединение

При попытке выполнить `npx prisma -v` (для проверки версии и загрузки бинарников движка Prisma) команда зависла и завершилась с ошибкой:

```
Error: request to https://binaries.prisma.sh/.../schema-engine.exe.gz.sha256 failed,
reason: getaddrinfo ENOTFOUND binaries.prisma.sh
```

Дальнейшая диагностика показала, что сеть недоступна полностью:
- `node -e "fetch(...)"` к npm registry, GitHub, GitHub Objects — везде `fetch failed`.
- `curl` к `registry.npmjs.org` — таймаут DNS-резолвинга.
- `npm ping` — `ENOTFOUND registry.npmjs.org`.
- `nslookup registry.npmjs.org` — DNS-сервер `1.1.1.1` не отвечает вообще ни на один запрос.
- Проверка `netsh winhttp show proxy` показала прямое подключение без прокси — то есть дело не в прокси-настройках, а в реальном отсутствии соединения на уровне сети/DNS.
- Повтор теста с `dangerouslyDisableSandbox: true` дал тот же результат — значит, это не ограничение песочницы инструмента, а реальный обрыв сети на машине.

## 7. Настройка автоматизации Claude Code (по просьбе пользователя)

Пользователь попросил: (1) разрешить Claude самостоятельно запускать команды разработки (npm/npx/git/docker) без подтверждения на каждый шаг, и (2) настроить автоматическое обновление `chat_history.md` после каждой остановки.

Реализовано в `.claude/settings.local.json` (личный, не коммитится — добавлен в `.gitignore`):

- **Permissions.allow**: `Bash(npm *)`, `Bash(npx *)`, `Bash(node --version|-v)`, безопасные git-команды (`status`, `diff`, `log`, `show`, `add`, `commit` — без `push`/`reset --hard`/force), `Bash(docker compose *)`, `Bash(docker-compose *)`, `Bash(docker --version)`. Деструктивные операции сознательно не добавлены в allow-list — для них по-прежнему будет запрос подтверждения.
- **Hooks.Stop**: bash-команда, которая при каждой остановке ищет файлы новее `chat_history.md` (исключая `.git`, `node_modules`, `.next`). Если такие есть — возвращает `{"decision":"block","reason":"..."}`, что заставляет Claude дописать сводку в `chat_history.md` перед завершением ответа. Если новых изменений нет — `{"continue":true}`. Команда протестирована в обеих ветках (block/continue) через прямой запуск в шелле.

## 9. Важная находка: баг `prisma dev` + `template1`, переход на `db push`

При попытке создать вторую миграцию (`add_employee`) `prisma migrate dev` стабильно падал на этапе применения к shadow-базе с ошибкой `type "Role" already exists`, хотя shadow-база была пуста. Причина: изначальная строка подключения (напечатанная самим `prisma dev --detach`) указывала на **`template1`** — служебную базу PostgreSQL, которая по умолчанию используется как шаблон для ЛЮБОЙ новой базы (`CREATE DATABASE` копирует её содержимое). Так как наши таблицы физически лежали в `template1`, каждая новая shadow-база (и любая другая новая база) автоматически наследовала уже существующие объекты — отсюда конфликт.

Что сделано:
- `template1` полностью очищена (DROP TABLE/TYPE) и оставлена пустой — as it should be.
- Заведена отдельная выделенная база **`easywork`**, на неё указывает `DATABASE_URL` в `.env`/`.env.example` (см. предупреждающий комментарий там же).
- Несмотря на очистку, `prisma migrate dev` продолжал давать сбои даже на новых именованных инстансах `prisma dev` (похоже на баг/квирк персистентности этой сравнительно новой фичи Prisma 7 — данные "просачивались" между инстансами непонятным образом). После нескольких попыток пересоздания решено **временно перейти на `npx prisma db push`** вместо `prisma migrate dev` — `db push` не использует shadow-базу вообще и сработал сразу и чисто.
- Папка `prisma/migrations/` удалена (она не соответствовала реальному состоянию БД при работе через `db push`). Как только будет доступен стабильный Postgres (Docker или собственная миграция `prisma dev` без этого бага), нужно будет сгенерировать нормальную историю миграций заново через `prisma migrate dev --name init`.
- **Практическое следствие**: пока используем `npx prisma db push` после каждого изменения `prisma/schema.prisma`, а не `migrate dev`. Это ок для сольной разработки на раннем этапе, но перед продакшеном/CI нужно будет вернуться к миграциям с историей.

Синглтон `PrismaClient` в `src/lib/prisma.ts` намеренно кэшируется в `globalThis` между Fast Refresh перезагрузками (чтобы не плодить соединения при hot reload) — но это же означает, что после `prisma generate` с новой моделью старый долгоживущий процесс dev-сервера продолжает держать в памяти старый инстанс клиента без `.employee`. Исправлено перезапуском dev-сервера (`taskkill` старого PID + свежий `npm run dev` в фоне) после свежего `prisma generate`. **Важно на будущее**: после любого изменения `prisma/schema.prisma` + `db push`/`generate` — dev-сервер нужно перезапускать, иначе будет та же ошибка.

## 21. Phase 7 — Модуль паролей (vault) реализован с упором на безопасность

Пользователь попросил сделать всё "качественно и безопасно" — это самый чувствительный модуль проекта (шифрование секретов), подошёл к нему с особым вниманием к проверке.

### Схема и шифрование

- `prisma/schema.prisma`: `VaultServiceEntry` (`ciphertext/nonce/authTag` — отдельные `Bytes`-поля, `status`/`archivedAt` как у других архивируемых сущностей), `EmployeeVaultAccess` (join `Employee↔VaultServiceEntry`, `grantedById`), `Tag`/`TagOnVaultEntry` (`kind: MANUAL | EMPLOYEE_ACCESS`), `VaultAccessLog` (аудит раскрытия секрета).
- `src/lib/crypto.ts` — AES-256-GCM. Двухуровневая схема ключей: мастер-ключ приложения (`ENCRYPTION_MASTER_KEY` из `.env`, 32 байта) оборачивает случайный per-org DEK (`Organization.encDekWrapped/encDekNonce`); каждый секрет шифруется собственным случайным nonce на DEK организации. `authTag` проверяется при расшифровке — при подмене шифротекста/тега/использовании неверного ключа выбрасывается исключение (не проглатывается молча).
- `src/lib/org-dek.ts` — `getOrgDek(orgId)` с ленивым бэкфиллом: если у организации ещё нет DEK (создана до Phase 7), он генерируется и сохраняется атомарно при первом обращении к vault.
- `registerAction` (регистрация) теперь сразу создаёт DEK для новой организации — бэкфилл нужен только для организаций, заведённых раньше.
- Технический нюанс: новые версии `@types/node`/TypeScript различают `Buffer<ArrayBufferLike>` и `Uint8Array<ArrayBuffer>`, а сгенерированный Prisma-клиент требует именно второе для `Bytes`-полей — пришлось явно материализовать чистые `Uint8Array<ArrayBuffer>` на границе с Prisma (`Uint8Array.from()`), иначе сборка не проходила.

### Бизнес-логика

- `src/actions/vault.ts` — CRUD записи (секрет write-only: на редактировании поле всегда пустое, если оставить пустым — пароль не меняется), `grantVaultAccess`/`revokeVaultAccess` (авто-тег на сотрудника создаётся лениво через `upsert`, переиспользуется между записями, при отзыве удаляется только связь тег↔запись, а не сам тег), `revealVaultSecret` — отдельное действие от обычного открытия карточки, пишет строку в `VaultAccessLog`.
- `src/actions/employees.ts::updateEmployee` — при переименовании сотрудника синхронизирует имя его авто-тега (с защитой от коллизии уникальных имён через try/catch, чтобы не сломать сохранение профиля).
- `lib/archive.ts` расширен: `vaultServiceEntry` архивируется вместо удаления, если у записи есть хоть один выданный доступ; `employee` теперь также проверяется на `EmployeeVaultAccess`, а не только на заказы.

### UI и контроль доступа

- Страницы `/[org]/vault`, `/new`, `/[id]` (карточка: раскрытие пароля, управление доступом сотрудников через комбобокс, недавние просмотры).
- **Проверка доступа — на уровне маршрута, не только в UI**: список и карточка вызывают `can(ctx.role, "vault", "read")` и делают `notFound()` для роли EMPLOYEE (а не просто прячут пункт меню — тот факт, что ссылка скрыта в сайдбаре, не мешает зайти по прямому URL).
- Подключен `<Toaster />` (sonner) в корневой layout — использован для обратной связи при архивации/удалении.

### Проверка (расширенный тест на 21 пункт, все прошли)

Написан временный скрипт, покрывающий именно то, что чаще всего ломается в подобных системах:
- round-trip шифрования; два шифрования одного текста дают разные nonce/шифротекст; порча шифротекста/authTag/использование чужого ключа — исключение;

## 23. Реальный баг из браузера пользователя + Phase 8 (полировка)

Пока писалась предыдущая сводка, пользователь сам покликал по приложению в браузере (`GET /prk/employees`, `GET /prk` — видно в логе dev-сервера). Это вскрыло реальное предупреждение в консоли:

**Исправлено централизованно** в `src/components/ui/button.tsx`: теперь `Button` сам выставляет `nativeButton={false}`, если передан кастомный `render`, и не трогает поведение по умолчанию для обычных кнопок. Один фикс в одном месте закрывает все 9 случаев сразу и защищает от повторения в будущем.

### Блок B — Склады и остатки (реализован целиком)

### Архитектурное решение: не заводить Demand/Supply как отдельные модели

Вместо создания новых моделей `Demand`/`Supply` (как буквально описано в ROADMAP) решил расширить уже существующий `StockMovement`/`StockMovementLine` двумя новыми типами — `DEMAND` (отгрузка, ведёт себя как `LOSS`) и `SUPPLY` (приёмка, ведёт себя как `ENTER`), плюс опциональные `orderId`/`purchaseOrderId` на `StockMovement` и `unitPriceSnapshot` на `StockMovementLine`. Это дало готовый леджер остатков "бесплатно" — `lib/stock.ts` не пришлось переписывать концептуально, просто добавить 2 типа в CASE-выражение. Меньше кода, меньше моделей, тот же уровень строгости (immutable-движения, `Restrict` на FK).

### Что реализовано

- **PurchaseOrder/PurchaseOrderLineItem** — заказ поставщику, зеркало `Order`, но `Client` используется как поставщик (`supplierId`), а не заводили отдельную модель `Supplier` — контрагент один список для обеих ролей.
- **`actions/fulfillment.ts`** — `createDemand`/`createSupply`: привязка к заказу/заказу поставщику, **защита от превышения количества** (нельзя отгрузить/принять больше, чем осталось по документу — считается как заказано минус уже отгружено/принято по всем предыдущим DEMAND/SUPPLY), цена/себестоимость берётся из строки заказа (снапшот на момент заказа), а не из текущей цены каталога.
- **`FulfillmentPanel`** (переиспользуемый компонент) — история движений + форма частичного/множественного исполнения, встроена и в карточку заказа ("Отгрузка"), и в карточку заказа поставщику ("Приёмка"). Только `PRODUCT` может участвовать (услуги/комплекты отфильтрованы и на клиенте, и проверкой на сервере).
- **`Payment`** (упрощённая версия C3, без полноценных счетов) — `IN`/`OUT`, привязка к контрагенту, `lib/balances.ts::getClientBalance` считает "должен нам"/"должны ему" отдельно (клиент может быть одновременно и покупателем, и поставщиком). Показывается на карточке клиента.

Реализовано ровно так, как и предполагалось в ROADMAP при откладывании — минимальное расширение существующего леджера, без новых моделей. `actions/fulfillment.ts::createSalesReturn`/`createPurchaseReturn` ограничивают возврат тем, что реально было отгружено/принято и ещё не возвращено. `FulfillmentPanel` расширен с 2 до 4 режимов (`kind`) через таблицы `ACTIONS`/`LABELS` — компонент не пришлось переписывать, только расширить конфигурацию.

### A3 — Модификации товара (наконец сделано, сознательно упрощённо)

`Characteristic` (справочник, напр. "Размер") + `CatalogItemVariant` (модификация с своими артикулом/штрихкодом/ценой) + `CatalogItemVariantValue`. **Ключевое упрощение, зафиксированное в ROADMAP**: варианты НЕ получили отдельный остаток — склад по-прежнему считает по базовому `CatalogItem`. Переделка леджера под гранулярность на уровне варианта — отдельная, более рискованная задача, не стал смешивать её с этим заходом. `OrderLineItem.variantId` позволяет заказать конкретную модификацию, цена берётся из `priceOverride` варианта, если задан.

### D2 (Договоры), D3 (Каналы продаж), D4 остаток (Контакты клиента)

Все три — простые справочники/связи, реализованы за один заход:
- `Contract` — номер + контрагент + дата подписания, опционально привязывается к `Order`/`PurchaseOrder`.
- `SalesChannel` — простой справочник, поле на `Order`.
- `ClientContact` — несколько контактных лиц на клиента (имя/должность/телефон/email), добавляются/удаляются прямо на карточке клиента.
- **D1 (несколько юрлиц компании) сознательно пропущен** — единственный пункт Блока D, который реально не нужен почти никому из целевой аудитории.

### Блок G — Отчёты, весь первый набор

- Обороты (`/reports/turnover`) — приход/расход по товару за период. `MOVE` намеренно исключён из расчёта (внутренний перенос, не изменение общего остатка).
- Деньги (`/reports/money`) — платежи за период + текущий денежный остаток (баланс за всё время, не поток за период).
- P&L (`/reports/pnl`) — **явно помечен в UI как упрощённый**: выручка по фактическим отгрузкам, себестоимость по фактическим приёмкам за тот же период, без партионного учёта (FIFO/средневзвешенная) — оценочная цифра, не бухгалтерская точность.
- Продажи по клиентам (`/reports/sales-by-client`) — сумма заказов/оплачено/задолженность.

**Зафиксировано известное ограничение**: все денежные отчёты складывают суммы разных валют арифметически без конвертации (курсов нет) — не проявляется, пока всё в одной валюте (сейчас везде RUB по умолчанию), но не настоящая мультивалютность.

## 33. Сотрудники "как в МойСклад" (в план), формат логина login@org (в работе), диагностика медленной загрузки

### Исследование МойСклад (фоновый агент, завершено)

Права доступа: 6 типов ролей (Владелец, Системный администратор, Кассир, Сотрудник производства, Пользовательская роль (`customrole`, переиспользуемая), Индивидуальная роль (`individualrole`, персональная)) — только на тарифах Professional/Corporate. Назначение роли — через `/entity/employee/{id}/security`.

Логин: подтверждено на реальных примерах из доступной документации — формат `login@accountname` (напр. `"uid": "admin@reqwy1"`), логин уникален только в рамках аккаунта, не глобально. ### Диагностика "медленной загрузки" — найдено две отдельные причины

1. **Реальный баг в коде, исправлен**: `src/lib/prisma.ts` создавал `pg.Pool` с настройками по умолчанию — без `keepAlive`, без обработчика `pool.on('error')`, без явного `idleTimeoutMillis`. Против прокси `prisma dev` (который агрессивнее закрывает простаивающие соединения, чем ожидает клиентский пул) это классически ведёт к "Connection terminated unexpectedly" на следующем запросе после простоя. Добавлены `keepAlive: true`, явный `idleTimeoutMillis: 10_000`, обработчик ошибок пула (без него необработанная ошибка на простаивающем клиенте вообще роняет процесс Node).
2. **Не баг кода, а нестабильность самой локальной БД** — при попытке засеять тестовые данные для замера производительности (~155 записей) `npx prisma dev` **падал по статусу `not_running` в течение 1-2 минут простоя и обрывался под нагрузкой прямо посреди скрипта** — воспроизведено трижды подряд экспериментально (не единичный случай). Это не решается правкой кода — `prisma dev` в принципе нестабилен в этом окружении при реальной нагрузке. Похоже, это и есть основной источник ощущения "долгой загрузки" (и не только загрузки — временами полного отказа), а не эффективность запросов приложения (N+1-паттернов в коде поиском не найдено).

### Спроектирована и написана единая схема под все 6 блоков разом

Чтобы не гонять `db push`/перезапуск dev-сервера по многу раз (см. известную нестабильность `prisma dev` — раздел про память проекта), весь набор изменений `prisma/schema.prisma` подготовлен одним заходом, до какой-либо бизнес-логики:

- **C4**: старые хардкод-enum'ы `OrderStatus`/`PurchaseOrderStatus` **полностью убраны**, вместо них новая модель `DocumentStatus` (per-org, `kind: ORDER | PURCHASE_ORDER`, `name/color/position/isFinal`) — конфигурируемый, но НЕ полноценный workflow-движок (без графа переходов и прав на переход, как и предполагалось при откладывании этого пункта). `Order.statusId`/`PurchaseOrder.statusId` — обязательные FK (`onDelete: Restrict`). - **Блок H2 (мультивалютность)**: `Organization.baseCurrency` (default RUB), новая модель `ExchangeRate` (per-org, `currency → rateToBase`, по дате). ## 43. C4 — граф переходов между статусами документов, по явному запросу

Пользователь получил список из 5 сознательно нереализованных пунктов, попросил уточнение и выбрал "C4 — граф переходов статусов" из предложенных вариантов.

### Реализация

- Новая модель `DocumentStatusTransition` (`fromStatusId`, `toStatusId`, `allowedRoles: Role[]`, `@@unique([fromStatusId, toStatusId])`) — additive-миграция, `db push` прошёл без запроса согласия.
- **Ключевое архитектурное решение — opt-in ограничение, не по умолчанию**: пока у статуса нет ни одной исходящей строки в `DocumentStatusTransition`, переход разрешён в любой другой статус того же вида документа (обратная совместимость: существующие организации, у которых 4 дефолтных статуса без единого правила, продолжают работать ровно как раньше). Как только добавлено хотя бы одно правило "из X" — статус X становится ограничен: только явно перечисленные направления. Это решение приняли сам, без уточняющего вопроса — единственный вариант, не ломающий уже работающие организации задним числом.
- `lib/document-statuses.ts::getAllowedNextStatusIds(orgId, kind, statusId, role)` — считает разрешённые следующие статусы с учётом `allowedRoles` (пустой список = доступно всем, у кого вообще есть право менять статус — это **дополнительное** сужение поверх `assertPermission`/`orderScope`, не замена им). `getSelectableStatuses` — то же самое + текущий статус (чтобы селект показывал текущее значение, даже если оно не является "разрешённым следующим" для самого себя).
- Enforcement на сервере: `updateOrderStatus`/`updatePurchaseOrderStatus` в `actions/orders.ts`/`purchase-orders.ts` теперь сначала читают текущий `statusId` заказа, и если новый статус отличается — проверяют `getAllowedNextStatusIds`, иначе `throw new Error("Такой переход между статусами запрещён")`. No-op (тот же статус) всегда проходит без проверки.
- UI: страницы `orders/[id]`/`purchase-orders/[id]` теперь зовут `getSelectableStatuses` вместо `listDocumentStatuses` для селекта — выпадающий список физически не содержит запрещённых опций, а не просто блокирует их выбор.
- Новый `DocumentStatusTransitionsManager` на `/settings/statuses`, под уже существующим списком статусов — таблица переходов + строка добавления (два `<select>` + чекбоксы ролей ADMIN/MANAGER/EMPLOYEE, пусто = все). У статусов с хотя бы одним исходящим правилом в выпадающем списке "Из статуса" помечено "(ограничен)".

### Проверка

- `npm run build` — чисто.
- Временный скрипт (`tmp-verify-transitions.mts`, удалён) — 7/7: без правил разрешено всё; после добавления `Черновик→Подтверждён` (все роли) + `Черновик→Отменён` (только ADMIN) — EMPLOYEE видит только "Подтверждён" как опцию, ADMIN видит оба; статус-сосед без своих правил (`Подтверждён`) остаётся неограниченным, даже когда у `Черновика` уже есть правила; `getSelectableStatuses` включает текущий статус.
- **Полный сквозной прогон в браузере** (`qa-transitions`, удалён после проверки): создал правило `Черновик→Подтверждён` (без ограничения по ролям) → создал заказ → в выпадающем списке статуса на карточке заказа реально показаны только "Черновик"/"Подтверждён" (не "Завершён"/"Отменён") → сменил статус на "Подтверждён" → в выпадающем списке снова стали доступны все 4 статуса, потому что у "Подтверждён" своих правил нет. Ни одной ошибки в консоли.

### Найденный и исправленный баг вёрстки (не из плана, всплыл при проверке)

Живой тест (`element.style.minWidth='0px'` через `run_code_unsafe`) подтвердил гипотезу до правки исходников. Исправлено добавлением `min-w-0` в этот div; заодно добавлен `min-w-0` в общие `Card`/`CardContent` (`ui/card.tsx`) как защита от той же проблемы для любой карточки с широким содержимым где-либо ещё в приложении.

## 49. Проверка на реальных устройствах (телефон/планшет) — найдено и исправлено 3 дополнительных бага

### Пройдено вживую на iPhone 15 (реальная touch-эмуляция)

### Найдено и исправлено 3 бага, невидимых на обычном десктопном Chrome без touch-эмуляции

1. **Хидрейшн-мисматч на КАЖДОМ текстовом поле на touch-устройстве.** `@base-ui/react`'s `Input` внутренне выставляет `style={{caretColor:"transparent"}}` по клиентской проверке coarse-pointer (скрывает мигающий курсор на touch), которая не может выполниться при SSR — сервер и клиент расходятся на первом рендере. Проявлялось на любой странице с текстовым полем (сначала думал, что только на `type="date"`, но полная трасса ошибки на карточке клиента показала: затрагивает буквально все инпуты). Исправлено `suppressHydrationWarning` в общем `ui/input.tsx` — по документированному React-паттерну именно для таких заведомо безопасных client-only расхождений.
