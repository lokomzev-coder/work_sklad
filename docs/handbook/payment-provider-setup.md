# Подключение платёжного провайдера — чек-лист

На момент написания этого документа платёжный провайдер сознательно **не
выбран и не подключён** — пользователь явно решил отложить это решение
до момента, когда провайдер определится (см. `ROADMAP.md`, Блоки L и Q).
С Блока Q в проекте есть полноценная балансовая система: у организации
есть предоплаченный баланс (`Organization.balance`), покупка тарифа
(готового или собранного в конструкторе) создаёт `SubscriptionInvoice`,
который списывается с баланса и автоматически выдаёт тариф
(`src/lib/billing/subscription-billing.ts`). Единственное, чего не
хватает — способа положить реальные деньги на этот баланс: сейчас это
делает вручную платформенный админ с карточки организации
(`/admin/organizations/[id]`, форма «Пополнить баланс»). Этот документ —
не инструкция «как настроено», а чек-лист «что именно нужно сделать»,
когда провайдер будет выбран — и, в отличие от версии этого документа до
Блока Q, у этой задачи уже есть точный, а не гипотетический шов
подключения (см. ниже).

## Точка подключения — уже существует, не нужно проектировать заново

Три функции в `src/lib/billing/subscription-billing.ts` — это тот же
принцип «один переключаемый адаптер», что уже применён к
`src/lib/fiscal/atol-provider.ts` (фискализация чеков) и
`ManualConfirmationAdapter` в рознице (оплата вручную, когда нет
терминала) — только адаптируемая сторона здесь не внешний протокол
эквайринга, а способ, которым баланс организации узнаёт, что деньги
пришли:

- **`creditBalance(orgId, amount, note, platformAdminId)`** — сегодня
  вызывается только из `creditOrganizationBalance`
  (`src/actions/platform-subscriptions.ts`), когда платформенный админ
  вручную жмёт «Пополнить баланс». Это ровно та функция, которую должен
  вызвать обработчик вебхука реального провайдера — с `platformAdminId:
  null` (зачисление автоматическое, не от человека) вместо
  `ctx.platformAdminId`. Она уже сама пишет `BalanceTransaction` и сразу
  пытается погасить старейший `PENDING`-счёт организации — «автовыдача»
  уже реализована на этом уровне, вебхуку останется только сообщить
  сумму и организацию.
- **`attemptSettleInvoice(invoiceId, opts)`** — вызывается изнутри
  `creditBalance` и `createOrDraftInvoice` автоматически; отдельно
  вызывать из вебхука не нужно.
- **`createOrDraftInvoice(orgId, selection)`** — формирует
  `SubscriptionInvoice` из выбора организации (готовый тариф или
  конструктор); вебхука не касается, разве что провайдер потребует
  заранее знать точную сумму до перевода денег (см. «Модель» ниже).

Значит подключение реального провайдера — это в первую очередь один
новый файл-адаптер и один новый вебхук-роут, который в конце просто
вызывает `creditBalance`, а не переработка всей балансовой системы:

1. Новый каталог `src/lib/billing/providers/` с единым интерфейсом
   (набросок, уточнить под выбранного провайдера):
   ```ts
   export interface PaymentProvider {
     createTopUpSession(input: { orgId: string; amount: number; returnUrl: string }): Promise<{ checkoutUrl: string }>;
     verifyWebhookSignature(rawBody: string, signature: string): boolean;
     parseWebhookEvent(rawBody: string): { orgId: string; amount: number; externalPaymentId: string } | null;
   }
   ```
   Конкретная форма интерфейса зависит от выбранного провайдера (не все
   провайдеры одинаково моделируют платежи/чекауты) — не проектировать
   вслепую заранее, скорректировать по документации реального провайдера
   на момент подключения.
2. Один файл-реализация под конкретного провайдера (`stripe-provider.ts`,
   `yookassa-provider.ts` и т.п.) — по образцу `atol-provider.ts`: явные
   типы входа/выхода, минимум состояния, ссылка на источник (документация
   провайдера) в комментарии, с честной пометкой, какие поля/коды
   подтверждены официальной документацией, а какие — нет (тот же принцип
   честности, что уже принят для АТОЛ-адаптера).
3. Новый роут `/api/billing/webhook` — проверяет подпись через
   `verifyWebhookSignature`, парсит событие, вызывает
   `creditBalance(orgId, amount, `Провайдер, платёж ${externalPaymentId}`, null)`.
   Дальше ничего вручную делать не нужно — активация тарифа, запись в
   `SubscriptionChangeLog`/`PlatformAuditLog` уже происходят внутри.
4. Точка переключения — один конфиг/фабрика (`getPaymentProvider()`),
   не разбросанные по коду импорты конкретного вендора.

## Что уже решено в Блоке Q (не пересматривать без причины)

Часть вопросов, стоявших здесь до Блока Q, уже закрыта архитектурой
балансовой системы, а не будущим провайдером:

- **Продление и грейс-период** — уже реализованы независимо от
  провайдера. `subscriptionExpiresAt` продлевается автоматически
  (`attemptSettleInvoice`), недельный грейс-период при неудачном
  списании и полное ограничение по его истечении вычисляются на лету
  (`resolveSubscriptionState`, `src/lib/subscription.ts`) и не завязаны
  на то, кто именно пополнил баланс — человек из панели или вебхук.
  Провайдеру не нужно ничего знать про грейс-период, только про баланс.
- **Аудит** — `attemptSettleInvoice` уже пишет и `SubscriptionChangeLog`
  (видно организации), и `PlatformAuditLog` (видно панели) при каждом
  списании, включая автоматическое продление. Вебхуку провайдера
  достаточно вызвать `creditBalance` — остальное произойдёт само.
- **Модель** — платежи всегда идут через баланс (пополнение), а не
  напрямую привязаны к конкретному тарифу/подписке провайдера —
  это уже снимает главный архитектурный вопрос, стоявший здесь раньше
  («разовые платежи или нативные подписки провайдера»): для этого
  проекта провайдер нужен только как способ пополнить баланс, тарифом
  и продлением по-прежнему управляет `subscription-billing.ts`.

## Что ещё нужно решить при выборе провайдера

- **Валюта и локаль**: `SubscriptionPlan.currency`/`Organization.baseCurrency`
  в схеме уже есть, но конвертация между валютами не реализована
  (`createOrDraftInvoice` сейчас явно отказывает, если валюта тарифа не
  совпадает с валютой организации) — если провайдер работает в другой
  валюте, потребуется либо конвертация на границе с провайдером, либо
  ограничение на валюту организации.
- **Хранение секретов провайдера** (API-ключ, webhook-secret): это
  секрет **платформы**, не организации — значит НЕ через
  органо-скоупенный DEK-механизм (`lib/org-dek.ts`, применяется к
  секретам конкретной организации, например паролю ОФД), а тем же
  способом, что уже сделан для TOTP-секретов платформенных админов —
  `encryptWithMasterKey`/`decryptWithMasterKey` из `lib/crypto.ts`
  (прямое использование `ENCRYPTION_MASTER_KEY`, без org-DEK). Секрет
  провайдера принадлежит всему проекту, а не одной организации, поэтому
  органо-DEK здесь концептуально неверен.
- **Webhook-эндпоинт**: по аналогии с уже существующими `/api/cron/*` и
  вебхуками фискализации — отдельный роут (например
  `/api/billing/webhook`), обязательная проверка подписи запроса
  (провайдер обычно подписывает тело HMAC'ом своим секретом — не
  доверять телу без проверки, иначе кто угодно сможет прислать поддельное
  «оплата прошла»).
- **Идемпотентность вебхука**: провайдеры могут присылать одно и то же
  событие повторно (retry на их стороне) — обработчик должен проверять,
  не зачислен ли уже этот `externalPaymentId`, прежде чем вызывать
  `creditBalance` повторно (в `BalanceTransaction` пока нет поля для
  внешнего id платежа — добавить при подключении конкретного провайдера,
  не раньше, чтобы не гадать заранее про формат id).

## Что НЕ делать

- Не хранить номера карт/платёжные реквизиты клиента в собственной базе
  ни в каком виде — это зона ответственности провайдера (PCI DSS),
  прокси через себя не нужен ни разовым платежам, ни подпискам, если
  провайдер сам предоставляет форму оплаты/чекаут-сессию (что верно почти
  для всех современных провайдеров — Stripe, ЮKassa, CloudPayments и т.п.
  все предоставляют готовую форму).
- Не подключать провайдера «частично» (например, только приём платежа
  без обработки вебхука об отмене/возврате) — половинчатая интеграция
  хуже её отсутствия, потому что создаёт иллюзию автоматизации там, где
  на деле кто-то должен вручную сверять реальные платежи с базой.
- Не привязывать логику лимитов тарифа (`checkEmployeeLimit` в
  `src/lib/subscription.ts` и его будущие аналоги) к самому факту оплаты
  напрямую — они уже читают `Organization.subscriptionPlanId`, который
  устанавливается один раз при успешной оплате (вебхуком) точно так же,
  как сейчас устанавливается вручную админом; переписывать эту часть не
  нужно.
