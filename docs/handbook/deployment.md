# Деплой — памятка для разработчика

Проект: Next.js 16 (App Router) + Prisma 7 (driver adapter, `@prisma/adapter-pg`)
+ PostgreSQL. Домен проекта — **worksklad.ru**. Везде ниже, где встречается
`ваш-домен.ру` в примерах конфигурации — на реальном сервере подставляйте
`worksklad.ru`.

**Фактический деплой (Блок T, 2026-09-15)**: собственный Linux-сервер
пользователя (Ubuntu 26.04, домашняя сеть, статический внешний IP,
`worksklad.ru` на reg.ru) — реализовано через **Docker Compose**, не
голый systemd+nginx+certbot, который описывает остальная часть этой
памятки (тот вариант остаётся ниже как общий справочный материал —
принципы те же, детали процесса отличаются). Реальные файлы:
`Dockerfile` (multi-stage, `node:22-slim`, `next.config.ts`'s
`output: "standalone"`), `docker-compose.prod.yml` (три сервиса:
`postgres` без публикуемого порта наружу вообще, `app`, `caddy` —
единственный с портами 80/443 наружу), `Caddyfile` (реверс-прокси +
автоматический TLS через Let's Encrypt, домен берётся из `CADDY_DOMAIN`),
`deploy/backup-db.sh` (ежедневный `pg_dump` через cron хоста, не
контейнер — переживает `docker compose down`).

Разница с общими инструкциями ниже, которая реально важна:
- **Postgres** — не отдельная systemd-служба, а контейнер на internal
  docker-сети, недоступной ни хосту, ни тем более интернету (см. п.6
  ниже — эффект тот же, механизм другой).
- **Процесс-менеджер** (п.3) — `restart: unless-stopped` в
  `docker-compose.prod.yml`, не systemd unit.
- **Reverse proxy + TLS** (п.4) — Caddy (автоматический TLS без ручного
  certbot), не nginx.
- **Миграции**: baseline-миграция уже сгенерирована
  (`prisma/migrations/00000000000000_init/`) — `prisma migrate deploy`
  прогоняется на первом деплое через одноразовый контейнер из
  промежуточного `builder`-таргета `Dockerfile` (лёгкий рантайм-образ не
  тащит сам CLI `prisma`, только `@prisma/client`/`pg`/`@prisma/adapter-pg`,
  которые реально нужны в рантайме) — `docker build --target builder -t
  worksklad-migrator . && docker run --rm --network worksklad_internal
  --env-file .env.production worksklad-migrator npx prisma migrate deploy`.
- **`src/lib/prisma.ts`**: пул подключений теперь зависит от
  `NODE_ENV` — `max: 10` в production (реальный Postgres), `max: 1`
  только для локального `prisma dev` (PGlite, однопоточный движок) —
  раньше было жёстко `1` с комментарием «это dev-only», что перестало
  быть верным ровно с этим деплоем.

## 1. Переменные окружения

Обязательные (см. `.env.example` в корне репозитория за актуальным
списком — не полагайтесь только на эту памятку, сверяйте перед каждым
деплоем, список мог измениться):

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | строка подключения к PostgreSQL (`postgresql://user:pass@host:5432/db`) |
| `ENCRYPTION_MASTER_KEY` | мастер-ключ, из которого выводятся DEK'и организаций (шифрование пароля вендора/ОФД и т.п. — `lib/crypto.ts`/`lib/org-dek.ts`). **Компрометация = компрометация всех секретов всех организаций.** См. [linux-server-hardening.md](./linux-server-hardening.md) про хранение и ротацию. |
| `CRON_SECRET` | bearer-токен, которым внешний планировщик авторизуется к `/api/cron/*` роутам (сейчас: `webhook-retries`, `fiscal-status`). Без него в production роуты возвращают 500. |
| `AUTH_SECRET` (NextAuth v5) | секрет для подписи сессий/JWT. **Уточните точное имя переменной в вашем `.env.example`** — NextAuth v5 поддерживает и `AUTH_SECRET`, и `NEXTAUTH_SECRET`; в момент написания этой памятки её содержимое не читалось (файл в `.gitignore`, не должен коммититься). |
| `INTERNAL_APP_ORIGIN` (Блок M4 фаза B) | origin (например `https://worksklad.ru`), на который серверный рендер PDF (`/api/print/pdf`) направляет свой headless-браузер — **обязателен в production** (роут отказывает без него, fail-closed, см. `lib/print/internal-origin.ts`), намеренно не берётся из заголовков запроса (`Host`/`X-Forwarded-Host` — оба подделываемы без прокси, который их вычищает; иначе это была бы готовая SSRF-дыра). |
| `ADMIN_PATH` (Блок S, необязательна) | публичный URL панели разработчика, по умолчанию `/admin`. Задайте нестандартное значение (например `/x7f2k9`), чтобы скрыть панель от ботов/сканеров, ищущих `/admin` — см. [admin-panel.md](./admin-panel.md#0-своя-ссылка-admin_path) за подробностями и оговоркой про то, что это дополнительный слой, а не замена настоящей защиты. **Не** называйте переменную с префиксом `NEXT_PUBLIC_` — значение не должно попадать в клиентский бандл. |

Никогда не коммитьте `.env` в git. Убедитесь, что `.gitignore` его
покрывает (обычно уже так).

## 2. Сборка и запуск

Стандартный Next.js production-цикл:

```bash
npm ci                      # чистая установка по package-lock.json
npx prisma generate         # генерирует TS-клиент Prisma под текущую схему
npm run build                # next build
npm run start                # next start — production-сервер
```

`prisma generate` **обязателен** перед каждым build/start после любого
изменения `prisma/schema.prisma` — сгенерированный клиент иначе не будет
знать о новых моделях/полях (в этом же проекте на dev-машине это уже не
раз ловилось: после `db push` сервер нужно было перезапускать именно по
этой причине).

Миграции на боевой БД: используйте `npx prisma migrate deploy` (не
`db push`) в реальном деплое — `db push` в этом проекте применялся только
на dev-окружении ради скорости итерации; `migrate deploy` применяет
версионированные миграции без интерактивных запросов и без риска
случайного дрейфа схемы. Если в репозитории ещё нет папки
`prisma/migrations` (разработка велась через `db push`) — перед первым
боевым деплоем нужно сгенерировать baseline-миграцию
(`npx prisma migrate dev --name init` на копии схемы, либо
`prisma migrate resolve` для существующей БД) — сверьтесь с
официальной документацией Prisma 7 под конкретно вашу ситуацию, это
решение зависит от состояния существующих окружений и не должно
приниматься по шаблону.

## 3. Процесс-менеджер

Не полагайтесь на голый `npm run start` в терминале — используйте
`systemd` (см. [linux-server-hardening.md](./linux-server-hardening.md)
за примером unit-файла) или PM2, чтобы процесс автоматически
перезапускался при падении/перезагрузке сервера.

## 4. Reverse proxy + TLS

Next.js слушает обычный HTTP-порт (по умолчанию 3000) — перед ним должен
стоять nginx или Caddy, терминирующий TLS (сертификат — Let's Encrypt) и
проксирующий на `localhost:3000`. Подробности — в
[linux-server-hardening.md](./linux-server-hardening.md).

## 5. Внешний планировщик (cron)

Два роута требуют регулярного вызова извне (Next.js сам ничего не
планирует — see M3/E scope notes в самих роутах):

- `GET /api/cron/webhook-retries` — повторные попытки доставки вебхуков.
- `GET /api/cron/fiscal-status` — поллинг статуса фискальных чеков в АТОЛ.

Оба ожидают заголовок `Authorization: Bearer <CRON_SECRET>` (в production
обязательно, `CRON_SECRET` должен быть задан). Настройте `cron`
(обычный Unix cron, или systemd timer) на самом сервере, вызывающий их
через `curl`, например:

```cron
* * * * * curl -fsS -H "Authorization: Bearer $CRON_SECRET" https://ваш-домен/api/cron/webhook-retries
* * * * * curl -fsS -H "Authorization: Bearer $CRON_SECRET" https://ваш-домен/api/cron/fiscal-status
```

(раз в минуту — разумная частота для обоих; при желании можно реже,
задержка в доставке чека/вебхука не критична, а не поллить вообще —
критично, тогда чек/вебхук зависает в PENDING навсегда).

## 6. Розница/касса на отдельном поддомене

Интерфейс кассы (`/kassa`, Блок E) — часть того же Next.js-приложения,
изолирован на уровне маршрутизации через route group `(kassa)` (не делит
`SidebarShell`/остальной layout с основным дашбордом), но **не требует
отдельного деплоя** — это тот же процесс, тот же build.

Если вы хотите, чтобы касса открывалась на отдельном поддомене (например,
`kassa.ваш-домен.ру` вместо `ваш-домен.ру/org-slug/kassa`), это делается
**на уровне reverse proxy**, без изменений в коде:

- Вариант А (проще, рекомендуется): один и тот же Next.js-процесс,
  nginx/Caddy на поддомене `kassa.ваш-домен.ру` делает `rewrite`/`proxy_pass`
  на тот же `localhost:3000`, но переписывает путь на
  `/${org}/kassa$request_uri` (org — фиксированная для этого поддомена
  организация, если у вас на сервере одна организация; если несколько —
  потребуется какой-то маппинг поддомен→org, которого сейчас в коде нет,
  это уже отдельная доработка мультитенантного роутинга, не часть Блока E).
- Вариант Б (полное разнесение): второй отдельный запущенный процесс
  того же кода (тот же build, тот же `.env`) слушает другой порт,
  reverse proxy направляет `kassa.ваш-домен.ру` на него. Оба процесса
  бьют в одну и ту же БД — состояние (смены, продажи) общее, просто
  UI-точка входа разная. Не даёт практической выгоды над вариантом А,
  кроме независимого перезапуска/масштабирования кассы отдельно от
  основного интерфейса — рассматривайте только если для этого есть
  конкретная причина (например, разная нагрузка/SLA).

Пример nginx-конфига для варианта А (набросок, адаптируйте под себя):

```nginx
server {
    server_name kassa.ваш-домен.ру;

    location / {
        proxy_pass http://localhost:3000/ВАША_ОРГАНИЗАЦИЯ/kassa;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

server {
    server_name ваш-домен.ру;

    location / {
        proxy_pass http://localhost:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

(TLS-блоки опущены для краткости — см.
[linux-server-hardening.md](./linux-server-hardening.md) за полным
примером с `certbot`.)

## 7. Серверный PDF (Блок M4 фаза B)

«Скачать PDF» в диалоге печати рендерит документ через headless Chromium
(`playwright`), а не просто открывает HTML-страницу — сам браузер уже
подтягивается `npm install` (пакет в `serverExternalPackages`-списке
Next.js по умолчанию, конфигурировать не нужно), но **сам браузер —
нет**: обязателен отдельный шаг после установки зависимостей на каждом
окружении (dev-машина, CI-образ, боевой сервер):

```bash
npx playwright install chromium
```

Без этого шага `chromium.launch()` (`lib/print/pdf-browser.ts`) упадёт —
никакого автоматического фолбэка на обычный HTML-print нет, "Скачать PDF"
просто вернёт ошибку. На Linux-сервере вдобавок нужны системные
библиотеки самого Chromium (шрифты, `libnss3` и т.п.) — Playwright ставит
их сам флагом `--with-deps`:

```bash
npx playwright install --with-deps chromium
```

Это тяжёлая зависимость: сам браузер — сотни мегабайт на диске, и
headless-процесс остаётся живым между запросами (singleton, см. lib/print/
pdf-browser.ts) — держит память постоянно, не только на время рендеринга
одного PDF. На типичном serverless-хостинге (Vercel и т.п.) постоянный
процесс в принципе не работает без специальной обвязки
(`@sparticuz/chromium` — облегчённая сборка под serverless-лимиты,
отдельная адаптация под конкретную платформу, не сделана в этом проекте).
На обычном сервере с процесс-менеджером (см. раздел 3) — работает как
есть.

Не забудьте `INTERNAL_APP_ORIGIN` (раздел 1) — без него роут
`/api/print/pdf` в production откажет сразу, не пытаясь угадать origin
из заголовков запроса.

## 8. Чек-лист перед первым боевым деплоем

- [ ] `.env` заполнен, не в git, права доступа `600` (см. hardening-документ).
- [ ] `ENCRYPTION_MASTER_KEY` сгенерирован криптостойко (не "пароль123"),
      сохранён в надёжном месте (менеджер секретов/офлайн-копия) — при
      потере станут нечитаемы все зашифрованные секреты организаций.
- [ ] `CRON_SECRET` задан, cron-задачи на оба `/api/cron/*` роута настроены.
- [ ] `npx prisma migrate deploy` (не `db push`) прогнан на боевой БД.
- [ ] PostgreSQL слушает только localhost/приватную сеть, не 0.0.0.0
      (см. hardening-документ).
- [ ] TLS настроен, HTTP редиректит на HTTPS.
- [ ] Прочитан [docs/handbook/retail-integrations/README.md](./retail-integrations/README.md),
      если розница/касса будет использоваться — там описано, что
      фискализация и приём карты по умолчанию не активны без
      дополнительной настройки.
- [ ] `npx playwright install --with-deps chromium` прогнан (в Docker-варианте
      деплоя это уже часть `Dockerfile`, вручную делать не нужно —
      проверить, что образ пересобран после любого изменения версии
      `playwright` в `package.json`), `INTERNAL_APP_ORIGIN` задан — иначе
      «Скачать PDF» (раздел 7) не работает.
