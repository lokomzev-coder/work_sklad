# Панель разработчика (`/admin`) — памятка для платформенных админов

Панель разработчика — отдельный контур управления **всеми** организациями
проекта: тарифы/подписки, платформенные администраторы и их роли, журнал
аудита. Она физически изолирована от обычного входа организаций (Блок L,
`ROADMAP.md`): отдельная таблица пользователей (`PlatformAdmin`, не
`User`), отдельная cookie сессии (`admin-session-token`), обязательный
TOTP (2FA) при каждом входе. Компрометация обычной учётки организации —
даже с ролью ADMIN — не даёт никакого пути в эту панель.

## 0. Своя ссылка (`ADMIN_PATH`)

По умолчанию панель живёт на `/admin` — везде в этой памятке ниже
подразумевается именно этот путь, если на сервере не задана переменная
окружения `ADMIN_PATH` (Блок S). Если она задана (например `ADMIN_PATH=
/x7f2k9`), то:

- панель открывается по новому пути (`/x7f2k9/login` вместо
  `/admin/login`, и так везде);
- буквальный `/admin/*` перестаёт отвечать вообще (`404`, без разбора —
  чтобы старый путь не работал как запасной вход);
- вся навигация внутри панели уже ссылается на новый путь сама — искать и
  подменять ссылки руками не нужно.

**Важно понимать честно**: это дополнительный слой (снижает шум от
ботов/сканеров, которые перебирают стандартные пути вроде `/admin`,
`/wp-admin` и т.п.), а **не замена настоящей защиты**. Настоящая защита —
то, что не меняется этим переключателем ни на йоту: отдельная сессия
(`admin-session-token`, физически не пересекается с обычным логином
организации), обязательный TOTP, rate limiting входа, и то, что каждая
страница и каждое действие панели проверяют права заново независимо от
факта захода по правильному URL (см. раздел 5). Смена ссылки не заменяет
ничего из этого — просто добавляется поверх.

Переменную задавайте на сервере (`.env` или окружение процесса), **не**
с префиксом `NEXT_PUBLIC_` — иначе значение попадёт в код, отдаваемый
браузеру, и весь смысл теряется. См.
[deployment.md](./deployment.md) за местом в общем списке переменных.

## 1. Локальный запуск/остановка сервера

Панель работает на том же Next.js-процессе, что и весь сервис — отдельно
её не поднять и не остановить.

```bash
# остановить dev-сервер (если запущен в фоне/другом терминале — Ctrl+C
# в его окне, либо найти и остановить процесс):
# Windows PowerShell:
Get-Process node | Stop-Process        # осторожно — останавливает ВСЕ node-процессы

# запустить заново:
npm run dev
```

`npm run dev` также поднимает Turbopack-компиляцию — первое открытие
любой страницы после старта (`/admin/login` включительно) будет заметно
медленнее (несколько секунд), это нормально, дальше страницы отдаются из
кэша.

Отдельно должна быть запущена локальная БД (`prisma dev`, PGlite) —
обычно уже работает в фоне отдельным процессом; если `npm run dev`
падает с ошибками подключения к БД, проверьте, жив ли этот процесс,
командой `npx prisma dev start easywork-dev` (или тем именем, что задано
в проекте).

**Важно про параллельные подключения**: PGlite (используется в dev-
режиме через `prisma dev`) — однопоточная встроенная база, у неё
жёсткий потолок в одно соединение. Если одновременно с `npm run dev`
запустить ещё один процесс, обращающийся к той же базе (например, разовый
скрипт через `tsx`), возможна нестабильная (не всегда воспроизводимая)
ошибка соединения — самое надёжное решение в моменте: остановить
`npm run dev`, выполнить разовый скрипт, затем поднять `npm run dev`
обратно. Эта проблема — особенность dev-окружения (PGlite), в production
на настоящем PostgreSQL её не будет.

## 2. Создание головного аккаунта (только один раз на проект)

Головной аккаунт (`isOwner: true`) — единственный, с безусловным полным
доступом ко всем разделам панели и всем организациям. Он **не**
создаётся через веб-форму (форма регистрации для такого аккаунта сама по
себе была бы главной дырой в защите) — только разовым интерактивным
CLI-скриптом:

```bash
npx tsx scripts/create-platform-owner.ts
```

Скрипт запросит email, имя, пароль (минимум 12 символов, дважды для
подтверждения), затем сгенерирует секрет TOTP и покажет QR-код прямо в
терминале — отсканируйте его в приложении-аутентификаторе (Google
Authenticator, Яндекс Ключ, Authy и т.п.) и введите код для подтверждения.
Если сканировать нечем — под QR-кодом печатается ключ вручную (base32) для
ручного добавления.

Скрипт откажется запускаться повторно, если головной аккаунт уже создан
— это ожидаемо, второй такой аккаунт не нужен и не поддерживается.

QR-код и секрет нигде не сохраняются (ни в файл, ни в лог) — только
разовый вывод в терминал. Если экран настройки был утерян/не завершён,
единственный способ восстановиться — попросить владельца пересоздать
доступ вручную через базу данных (crypto-секрет TOTP не хранится в
восстановимом виде без прохождения повторной настройки).

## 3. Вход в панель

Откройте `/admin/login` (например `http://localhost:3000/admin/login` в
разработке). Форма отдельная от обычного входа организации — три поля за
один шаг: email, пароль, 6-значный код из приложения-аутентификатора.

Действует более строгий лимит попыток входа, чем у обычного логина
организации: **5 неудачных попыток за 15 минут** (по паре email+IP),
дальше — временная блокировка. Каждая попытка входа (успешная, неверный
пароль/код, блокировка по лимиту) пишется в журнал аудита панели.

## 4. Приглашение других платформенных админов (self-service, без передачи паролей)

Владелец (или любой админ с правом «Администраторы») может пригласить
нового платформенного админа на странице **Администраторы**
(`/admin/admins`) — указывается email, имя и (опционально сразу) роль.

Принципиально: **приглашающий никогда не видит пароль и TOTP-секрет
нового админа** — это его собственная зона ответственности. Приглашение
создаёт запись без пароля, с одноразовой ссылкой настройки (действует 24
часа) вида `/admin/setup/<токен>`. Эту ссылку нужно передать новому
админу лично или по защищённому каналу (в проекте нет встроенной
email-рассылки — так же, как и для приглашений в саму организацию).

По этой ссылке новый админ сам:
1. задаёт себе пароль;
2. сканирует свой собственный QR-код TOTP;
3. подтверждает код из приложения — только после этого аккаунт
   активируется и появляется возможность войти на `/admin/login`.

Если ссылка потеряна или просрочена — приглашение нужно выдать заново
(старый токен становится недействителен).

## 5. Роли и права доступа

Раздел **Роли** (`/admin/roles`) — гибкий набор из четырёх независимых
прав (capability), включаемых чекбоксами при создании/редактировании
роли:

| Право | Что открывает |
|---|---|
| `viewOrganizations` | просмотр списка и карточек организаций |
| `manageSubscriptions` | назначение/смена/отзыв тарифа у организации, управление самими тарифами |
| `manageAdmins` | приглашение платформенных админов, назначение им ролей, включение/отключение, создание/изменение ролей |
| `viewAuditLog` | просмотр журнала аудита (содержит IP-адреса и историю попыток входа — выделено в отдельное право, а не объединено с `manageAdmins`, из-за чувствительности этих данных) |

У головного аккаунта (`isOwner: true`) все права всегда включены
безусловно — это зашито в коде, а не выдаётся через роль, поэтому
владельца невозможно случайно разжаловать, отредактировав роль или
удалив её.

Ограничения, которые нельзя обойти через UI:
- нельзя отключить (`status`) головной аккаунт;
- нельзя отключить самого себя (админ с правом `manageAdmins` не может
  случайно отрезать себе доступ без возможности восстановиться);
- роль нельзя удалить, если она назначена хотя бы одному админу.

Навигация панели показывает только те разделы, на которые у
залогиненного админа есть право — но это исключительно для чистоты
интерфейса. Реальная проверка прав происходит независимо на каждой
странице и в каждом server action, поэтому попытка открыть URL раздела
напрямую, минуя навигацию, без нужного права вернёт ошибку доступа, а не
тихо покажет данные.

## 6. Организации, тарифы и баланс

С Блока Q подписка организации может оформляться **и** платформенным
админом вручную (как раньше), **и** самой организацией — self-service, со
страницы `/[org]/settings/subscription`. Панель разработчика остаётся
источником истины и полного контроля: видит баланс, счета и историю
любой организации, может вручную пополнить баланс или назначить/сменить/
отозвать тариф напрямую, в обход счетов.

Раздел **Организации** (`/admin/organizations`) — список всех организаций
проекта с поиском по названию. Карточка организации (`/admin/organizations/[id]`)
показывает:
- основные данные (slug, число участников, дата создания);
- **баланс** организации и форму ручного пополнения (см. ниже), если есть
  право `manageSubscriptions`;
- текущий тариф и дату истечения подписки — с формой прямого назначения
  тарифа, если есть право `manageSubscriptions` (иначе — только просмотр);
- список **счетов** (`SubscriptionInvoice`) — ожидающих оплаты, оплаченных,
  отменённых;
- полную историю изменений подписки (выдана/изменена/отозвана/истекла,
  кто и когда — включая записи, сделанные самой организацией через
  self-service, там `кто` будет пустым).

Каждое изменение тарифа — и ручное, и self-service — пишется в двух
местах одновременно: в историю самой организации (её видно и самой
организации — раздел «Подписка» в настройках) и в общий журнал аудита
панели.

Раздел **Тарифы** (`/admin/plans`) — CRUD готовых тарифных планов:
название, лимит сотрудников, лимит заказов в месяц (пусто = без лимита,
это не ноль), JSON-флаги фич, цена. Тариф нельзя удалить, если он
назначен хотя бы одной организации. Список показывает только общие,
переиспользуемые тарифы — приватные «Свои тарифы», которые организации
собирают себе сами через конструктор, здесь не отображаются (они видны
только на карточке конкретной организации, которой принадлежат).

### 6.1. Баланс и ручное пополнение

Организация оплачивает подписку с предоплаченного баланса (в валюте
организации). Пока не подключён реальный платёжный провайдер (см.
[payment-provider-setup.md](./payment-provider-setup.md)), единственный
способ пополнить баланс — вручную, из панели: на карточке организации
укажите сумму и комментарий (например, номер платёжного поручения) и
нажмите «Пополнить баланс».

Пополнение — не изолированное действие: если у организации уже есть
неоплаченный счёт (`PENDING`) и внесённой суммы теперь хватает, счёт
**оплачивается и тариф активируется автоматически в тот же момент**, без
дополнительных действий с чьей-либо стороны. Это и есть «автовыдача» —
сегодня платёж эмулирует платформенный админ вручную, при подключении
реального провайдера его вебхук будет вызывать ровно ту же внутреннюю
функцию (`creditBalance` в `src/lib/billing/subscription-billing.ts`).

### 6.2. Конструктор («Свой тариф»)

Раздел **Конструктор** (`/admin/feature-catalog`) — каталог пунктов, из
которых организация сама собирает индивидуальный тариф на своей странице
подписки. Каждый пункт — это:
- **Функция** (`FEATURE`) — включаемая опция с фиксированной ценой в
  месяц (просто вкл/выкл);
- **Доп. место сотрудника** (`EXTRA_EMPLOYEE_SEAT`) — организация
  указывает количество, каждая единица добавляет +1 к лимиту сотрудников
  за отдельную цену.

Итоговая цена «Своего тарифа» — сумма выбранных пунктов; лимит
сотрудников — единица (базовая вместимость конструктора) плюс купленные
доп. места. Пункт нельзя удалить — только архивировать (кнопка
«Архивировать» на странице пункта): архивный пункт пропадает из выбора
у организаций, но не портит уже выставленные счета (сумма исторического
счёта заморожена на момент покупки и не пересчитывается при изменении
каталога).

При создании/редактировании пункта каталога (Блок S) есть чекбокс
**«Включено в любую подписку бесплатно»** — если отметить, эта функция
считается доступной всем организациям безусловно, независимо от их
тарифа: не предлагается к покупке ни в конструкторе, ни в докупке
отдельной функции (раздел 6.4), и реальное ограничение (если оно есть у
этой функции) снимается для всех. Это и есть ответ на вопрос «что входит
в любую подписку» — настраивается здесь, по одной функции за раз, а не
общим переключателем.

**Что панель сознательно не умеет** (осознанный вырез объёма, не
недоделка): реальное списание оплаты через платёжного провайдера (см.
[payment-provider-setup.md](./payment-provider-setup.md) — подключается
отдельно, когда провайдер выбран) и режим «войти от имени организации»
для поддержки/отладки — оба требуют отдельного, отдельно аудируемого
контура, который не начат намеренно.

### 6.3. Пробный период и ограничение доступа

Каждая новая организация получает 14 дней полного доступа с момента
регистрации, без необходимости выбирать тариф. Если по истечении этого
срока (или по истечении недельного льготного периода после неудачного
автопродления оплаченного тарифа) подписка не оформлена — организация
переходит в состояние «доступ ограничен»: все сотрудники видят баннер об
этом, продолжают видеть свои данные (создание/редактирование документов
заблокировано), а ADMIN организации видит ссылку на страницу подписки,
чтобы восстановить доступ. Это состояние нигде не хранится отдельным
полем — оно каждый раз вычисляется заново из дат тарифа/пробного периода
(`resolveSubscriptionState` в `src/lib/subscription.ts`), поэтому не
может «зависнуть» рассинхронизированным с реальностью.

### 6.4. Гибкие функции по тарифам — что реально ограничено, а что нет

Раздел **Тарифы** (`/admin/plans/[id]`) теперь показывает не только
лимиты, но и чек-лист функций из каталога конструктора (раздел 6.2) —
каждая функция либо входит в этот тариф, либо нет (галочка). Функции,
отмеченные «включено всем бесплатно» на самом пункте каталога, показаны
здесь уже отмеченными и недоступны для снятия — они входят в любой тариф
по определению.

**Честно о том, что из этого реально работает как ограничение в
сервисе**, а что — просто информационная галочка для конструктора:
сегодня реальную проверку («эта функция правда недоступна, если её нет в
тарифе») проходят только три ключа — заведите пункт каталога именно с
таким `key`, чтобы ограничение включилось:

| Ключ | Что ограничивает |
|---|---|
| `retail` | Розничный модуль (`/kassa`) — без функции сотрудник с ролью «Кассир» видит страницу «недоступно» вместо кассы. |
| `production` | Производственный модуль (`/floor`) — то же самое для роли «Производство». |
| `custom_roles` | Создание новых гибких ролей (настройка прав) в самой организации — уже существующие роли продолжают работать, ограничивается только создание новых. |

Любой другой ключ каталога — обычный платный пункт конструктора/докупки,
без технического ограничения где-либо в сервисе (это не пробел, а
честно заявленный текущий объём — тот же механизм `assertFeatureEnabled`
в `src/lib/subscription.ts` подключается к новым частям сервиса по
одному и тому же образцу, когда это понадобится).

**Важная защита от несчастного случая**: если пункта каталога с
конкретным ключом ещё вообще не существует (админ ещё не завёл, скажем,
`retail`), сервис не ограничивает эту функцию вообще ни для кого — она
считается «пока не настроена», а не «отключена всем». Ограничение
начинает реально действовать только с момента, когда пункт каталога
заведён и явно не входит в тариф организации.

**Докупка функции отдельно, без смены тарифа**: на странице организации
`/[org]/settings/subscription` под сравнением тарифов есть блок
«Дополнительные функции» — там показаны все функции каталога, которых
нет в текущем тарифе организации и которые не бесплатны всем. Кнопка
«Докупить» добавляет ровно эту функцию поверх уже действующего тарифа
(остальные функции и лимит сотрудников сохраняются), списывает с баланса
только её цену — и, что важно, **не продлевает и не сбрасывает** срок
действия текущей подписки (в отличие от покупки/продления целого
тарифа). Технически это тот же биллинг-движок
(`createOrDraftInvoice`/`attemptSettleInvoice` в `src/lib/billing/
subscription-billing.ts`), новая ветка `kind: "ADD_ON"`.

## 7. Журнал аудита

Раздел **Журнал аудита** (`/admin/audit-log`) — полная лента действий
платформенных админов: входы (успешные и неудачные), блокировки по
лимиту попыток, изменения подписок, создание/изменение админов и ролей.
Каждая запись — кто (если применимо), что, когда, иногда IP. Можно
отфильтровать по конкретной организации (ссылка «Журнал аудита по этой
организации» есть прямо на карточке организации).

Это единственный источник правды о том, кто и что менял в панели — если
что-то выглядит подозрительно (незнакомый вход, неожиданное изменение
тарифа), начинайте разбор отсюда.

## 8. Что делать при подозрении на компрометацию

- Отключите (`status`) подозрительный аккаунт админа на странице
  **Администраторы** — доступ пропадает немедленно (сессии не
  переиспользуются после следующей проверки контекста).
- Просмотрите журнал аудита за подозрительный период — что именно было
  изменено под этой учёткой.
- Головной аккаунт скомпрометировать через UI нельзя разжаловать/удалить
  — если скомпрометирован именно он (пароль или TOTP-устройство),
  единственный путь — сменить пароль и перенастроить TOTP напрямую через
  базу данных (UI для этого намеренно нет, как и для первичного
  создания).
- Пароль головного аккаунта и секрет TOTP нигде за пределами базы (в
  зашифрованном виде) и памяти пользователя не хранятся — восстановить
  их иначе, чем через сброс, невозможно, это осознанное решение в пользу
  безопасности, а не недоработка.
