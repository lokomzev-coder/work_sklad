# Приём оплаты картой через физический терминал

## Текущее состояние (v1): ручное подтверждение

Когда кассир выбирает оплату картой, интерфейс кассы показывает
«Ожидание оплаты картой…» и две кнопки — «Оплата получена» / «Отменить».
Реального обращения к банковскому терминалу **не происходит** — кассир
сам смотрит на экран терминала (одобрено/отклонено) и подтверждает
результат в интерфейсе. Это `ManualConfirmationAdapter`
(`src/lib/terminal/manual-confirmation-adapter.ts`), реализующий интерфейс
`PaymentTerminalAdapter` (`src/lib/terminal/payment-terminal-adapter.ts`).

Это не заглушка "на будущее" в плохом смысле — это осознанный рабочий
режим: касса полностью функциональна и без интеграции с терминалом,
эквайринг просто идёт мимо кода (терминал и касса — два независимых
устройства на прилавке, как это часто бывает и в реальных небольших
магазинах).

## Почему нельзя просто "подключить терминал через USB и всё"

Браузер (и Next.js-сервер, на котором работает касса) **не может**
напрямую говорить с USB/COM-портом, к которому подключён банковский
терминал — это не файл и не сетевой сокет, а последовательный протокол,
требующий доступа к оборудованию ОС. Все настоящие интеграции (1С:Розница,
Frontol, r_keeper и т.д.) решают это через **отдельную локальную службу
("мост"/"драйвер") на самом кассовом ПК**, которая:

- работает как фоновый процесс на Windows/Linux кассового компьютера;
- имеет доступ к COM/USB-порту терминала;
- поднимает локальный HTTP-сервер (обычно `http://localhost:PORT`), к
  которому обращается кассовое ПО.

То есть архитектура для реальной интеграции выглядела бы так:

```
Браузер кассира (/kassa)  →  локальный HTTP-запрос  →  служба-мост на ПК  →  COM-порт  →  терминал
        │
        └─ через Next.js-сервер такой запрос НЕ идёт — сервер может быть
           не на этом же ПК; обращение к мосту должно быть client-side,
           напрямую с браузера кассира на localhost.
```

Это значит, что при переходе на реальный терминал `checkoutSale`
(`src/actions/retail-sales.ts`) не будет напрямую вызывать адаптер
терминала на сервере, как сейчас (`ManualConfirmationAdapter` безопасно
вызывать на сервере, потому что она ничего реального не делает) —
серверное действие должно будет **принять уже готовый результат оплаты**
(добытый клиентским кодом кассы через мост), а не сам инициировать оплату.
Это archитектурная правка, которую нужно будет сделать в момент реальной
интеграции — сейчас `PaymentTerminalAdapter.requestPayment()`
вызывается server-side намеренно просто, т.к. v1-реализация ничего не
делает с реальным железом.

## Какой протокол использовать

Исследование открытых источников на момент разработки показало: самый
распространённый протокол среди российских банков-эквайеров —
**INPAS SmartSale (он же DualConnector)**. Подтверждена поддержка у
Т-Банка (Тинькофф), ВТБ, Открытия, Точки — обычно с терминалами
Verifone/PAX, подключёнными по COM-порту (в том числе через
USB-to-COM adapter, если сам терминал/ПК не имеет физического COM).

**Важно**: точный байтовый протокол DualConnector не является публичной
открытой спецификацией — банки обычно выдают SDK/документацию/тестовый
терминал только своим подключённым мерчантам. Поэтому в этом проекте он
**не реализован** — только задокументированный набросок в
`src/lib/terminal/inpas-smartsale-adapter.ts` (класс закомментирован, но
показывает предполагаемую форму: `comPort`, `terminalId` в конфиге).

## Что вам нужно сделать, чтобы подключить реальный терминал

1. **Выбрать банк-эквайер** (если ещё не выбран) и уточнить у него:
   - поддерживает ли он INPAS SmartSale/DualConnector или у него свой
     протокол/SDK;
   - как получить тестовый терминал и тестовые учётные данные для
     проверки без реальных денег.
2. **Получить от банка**: SDK или протокол-документацию, драйвер/службу
   моста (иногда банк сам предоставляет готовую службу для установки на
   кассовый ПК — тогда самому писать байтовый протокол не нужно, только
   HTTP-клиент к их локальному API).
3. **Реализовать** (когда данные из п.1-2 на руках):
   - если банк даёт готовую локальную службу с HTTP API — дописать
     клиентский (браузерный) код в `src/components/kassa/pos-screen.tsx`,
     который делает `fetch` на `http://localhost:PORT/...` этой службы,
     и передаёт результат в серверное действие вместо текущего
     `waitingForCard`-паттерна;
   - если нужно говорить с портом напрямую (реже) — потребуется своя
     локальная служба-мост (например, на Node.js с библиотекой `serialport`
     для COM), реализующая DualConnector по документации банка, плюс
     `InpasSmartSaleAdapter` в `inpas-smartsale-adapter.ts`, довершающий
     интерфейс `PaymentTerminalAdapter`.
4. **Протестировать на тестовом терминале банка** перед боевым
   использованием — это одобрено платёжной системой требование (тестовые
   транзакции через тестовый терминал, не через боевой).

## Резюме для тестирования сейчас (без терминала)

Пока у вас нет банковского терминала/протокола — касса полностью рабочая
в режиме ручного подтверждения. Это нормальный v1: продавец физически
принимает оплату на отдельном терминале (как обычно и происходит сегодня
во множестве небольших магазинов, где касса и эквайринг — разные
устройства), а в кассовой программе просто отмечает факт оплаты.
