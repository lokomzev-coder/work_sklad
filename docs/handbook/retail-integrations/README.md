# Розница (касса) — интеграции: обзор

Этот раздел — для разработчика/владельца проекта, который будет **включать и
проверять** два внешних интеграционных контура кассы (Блок E ROADMAP):

1. **Фискализация чеков через ОФД** — [atol-fiscalization.md](./atol-fiscalization.md)
2. **Приём оплаты картой через физический терминал** — [card-terminal.md](./card-terminal.md)

## Почему это отдельная папка

Оба контура написаны честно, но **не проверены живым вызовом** — на момент
реализации не было ни тестового аккаунта АТОЛ, ни физического
банковского терминала. Код построен по открытой документации и общей
архитектуре, спроектирован так, чтобы:

- отсутствие настроенных credentials/железа **никогда не блокировало
  реальную продажу** (кассир всегда может пробить чек, даже если ни ОФД,
  ни терминал не подключены);
- переход на настоящее железо/аккаунт требовал **только конфигурации**,
  а не переписывания бизнес-логики кассы (`src/actions/retail-sales.ts`
  не знает, какой именно провайдер ОФД или какой именно терминал
  используется — только чистые интерфейсы).

## Архитектура в двух словах

```
Касса (/kassa) → checkoutSale()
                     │
                     ├─→ PaymentTerminalAdapter.requestPayment()   (если оплата картой)
                     │      └─ v1: ManualConfirmationAdapter — кассир подтверждает вручную
                     │      └─ будущее: адаптер под конкретный банк/терминал
                     │
                     └─→ (после проведения продажи, не блокируя её)
                          registerFiscalReceipt()
                             └─ AtolOnlineProvider — реальный HTTP-клиент АТОЛ Online v4
                                (не вызывается, если у org не настроены fiscal*-поля)
```

Оба места — единственные "швы", через которые проект будет говорить с
реальным миром:

| Файл | Роль |
|---|---|
| `src/lib/terminal/payment-terminal-adapter.ts` | интерфейс `PaymentTerminalAdapter` |
| `src/lib/terminal/manual-confirmation-adapter.ts` | v1: рабочая заглушка (ручное подтверждение) |
| `src/lib/terminal/inpas-smartsale-adapter.ts` | НЕ реализован — задокументированный набросок |
| `src/lib/fiscal/atol-provider.ts` | реальный клиент АТОЛ Online v4 |
| `src/lib/fiscal/credentials.ts` | хранение credentials организации (шифрование) |
| `src/lib/fiscal/register-fiscal-receipt.ts` | fire-and-forget регистрация + поллинг статуса |
| `src/app/api/cron/fiscal-status/route.ts` | внешний планировщик дёргает это для поллинга |

## Что нужно сделать вам, чтобы протестировать по-настоящему

Коротко (подробности — в файлах ниже):

1. **Фискализация**: зарегистрироваться в личном кабинете АТОЛ Online
   (тестовая группа), получить `login`/`password`/`group_code`, прописать
   их через `setFiscalConfig()` (см. `atol-fiscalization.md` — в v1 нет
   UI настроек, это одноразовый скрипт), пробить тестовую продажу,
   проверить `FiscalReceipt.status` в БД.
2. **Терминал**: связаться с вашим банком-эквайером, узнать — поддерживают
   ли они INPAS SmartSale/DualConnector, попросить SDK/протокол и тестовый
   терминал. До этого касса работает в режиме ручного подтверждения
   оплаты картой (кассир видит на терминале успешную оплату сам и жмёт
   кнопку в интерфейсе — деньги реально не проверяются кодом).

## Важная оговорка про АТОЛ

Коды полей `payment_method`/`payment_object`/`vat.type` и структура
запроса взяты из **нескольких независимых открытых источников** (статьи,
опубликованные PHP-клиенты), но не сверены с официальным PDF-протоколом
АТОЛ (попытки скачать/отрендерить его в ходе разработки не удались).
**Перед первой реальной отправкой чека — свяжитесь с документацией на
your-account.atol.ru или в личном кабинете и сверьте эти значения.** Все
такие места в коде помечены комментарием `// TODO: verify against the
official ATOL Online v4/v5 protocol PDF`.
