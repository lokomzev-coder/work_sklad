# Фискализация чеков — АТОЛ Online

## Что это и зачем

По 54-ФЗ каждая розничная продажа в РФ должна пробивать фискальный чек
через оператора фискальных данных (ОФД) и передавать его в ФНС. АТОЛ
Online — облачный сервис, который берёт эту работу на себя: вы шлёте ему
JSON с составом чека по HTTPS, он сам печатает/регистрирует фискальный
документ на своей стороне (без необходимости физического фискального
регистратора у вас).

В этом проекте фискализация **полностью опциональна на уровне
организации** — если у org не заполнены fiscal-настройки, касса работает
как обычно, просто не создаёт `FiscalReceipt`. Ни один продавец никогда
не будет заблокирован отсутствием ОФД.

## Шаг 1 — регистрация в АТОЛ Online

1. Зайти на https://online.atol.ru, зарегистрировать аккаунт (можно
   тестовый/демо-режим — уточните у АТОЛ актуальные условия тестового
   доступа на момент подключения).
2. В личном кабинете создать **группу ККТ** (group code) — виртуальную
   кассу, к которой будут привязываться чеки.
3. Получить:
   - `login`, `password` — учётные данные для API (НЕ пароль от личного
     кабинета — обычно отдельные API-креды, уточните в разделе
     интеграции/API вашего кабинета);
   - `group_code` — код группы ККТ;
   - реквизиты вашей организации: ИНН (`inn`), адрес расчётов
     (`payment_address` — обычно адрес точки продаж или сайт), система
     налогообложения (`sno` — например `osn`, `usn_income` и т.д., точный
     список кодов — в личном кабинете/документации АТОЛ).

## Шаг 2 — прописать credentials в проект

В v1 нет страницы настроек в интерфейсе (сознательный вырез объёма —
см. ROADMAP Блок E). Учётные данные хранятся зашифрованными на
`Organization` (поля `fiscalProvider`/`fiscalGroupCode`/`fiscalInn`/
`fiscalPaymentAddress`/`fiscalSno` — открытым текстом, `login`/`password`
— зашифрованы через `lib/crypto.ts`/`lib/org-dek.ts`, тем же примитивом,
что использует хранилище паролей, но без самой модели хранилища — эти
данные читает фоновый код, а не человек через UI).

Прописать их можно одноразовым скриптом. Пример (выполнить через
`npx tsx` из корня проекта, подставив реальные значения и ID организации):

```ts
// scratch-set-fiscal-config.ts (временный файл, не коммитить)
import { setFiscalConfig } from "./src/lib/fiscal/credentials";

await setFiscalConfig("ORG_ID_ЗДЕСЬ", {
  provider: "ATOL_ONLINE",
  groupCode: "ваш-group-code",
  inn: "ваш-инн",
  paymentAddress: "https://example.com или адрес точки",
  sno: "osn",
  login: "ваш-api-login",
  password: "ваш-api-password",
});
console.log("OK");
```

`ORG_ID_ЗДЕСЬ` — это `Organization.id` из БД (можно посмотреть в Prisma
Studio: `npx prisma studio`, таблица `Organization`).

## Шаг 3 — проверить

1. Открыть смену на кассе (`/kassa`), пробить тестовую продажу.
2. После продажи в БД должна появиться строка `FiscalReceipt` со
   `status: PENDING` и заполненным `atolUuid` (если запрос к АТОЛ прошёл
   успешно) либо `status: FAILED` с текстом ошибки в поле `error` (если
   что-то не так с credentials/форматом запроса).
3. Регистрация в АТОЛ асинхронна — статус `PENDING` меняется на
   `REGISTERED`/`FAILED` только после поллинга `GET report/{uuid}`.
   В проекте это делает `pollPendingFiscalReceipts()`
   (`src/lib/fiscal/register-fiscal-receipt.ts`), вызываемый через
   `GET /api/cron/fiscal-status` — см. [deployment.md](../deployment.md)
   про настройку внешнего планировщика (cron), который должен дёргать
   этот роут регулярно (например, раз в минуту). Пока планировщик не
   настроен, можно вызвать роут вручную (curl/браузер) для проверки.
4. Если `NODE_ENV=production` и `CRON_SECRET` задан — роут требует
   заголовок `Authorization: Bearer <CRON_SECRET>`.

## На что обратить внимание перед боевым использованием

- **Коды `payment_method`/`payment_object`/`vat.type`** в
  `src/lib/fiscal/atol-provider.ts` взяты из открытых источников, но
  **не сверены с официальным протоколом АТОЛ** — см. комментарии
  `// TODO: verify...` в этом файле.
- **Ставка НДС (`vat.type`) — обновление, Блок O фаза 2**: раньше на весь
  чек всегда шло `"none"` (без НДС), потому что каталог товаров вообще не
  хранил ставку. Теперь у каждого товара есть поле «Ставка НДС» (карточка
  товара, `CatalogItem.taxRate`) — по умолчанию «Без НДС» для всех
  существующих товаров (поведение не изменилось, пока вы явно не зададите
  ставку), значения: 0%/10%/20% (накладываются на цену) и 10/110, 20/120
  (НДС уже включён в цену — обычный случай для розницы с ценником на
  полке). Если ваша организация работает с НДС — задайте нужную ставку на
  каждом товаре в каталоге перед включением фискализации на боевом
  аккаунте; сами коды всё ещё не сверены с официальным протоколом (см.
  пункт выше).
- Тестируйте сначала на тестовой/демо-группе АТОЛ, не на боевой,
  привязанной к реальной кассе в налоговой.
- `email` покупателя в чеке — сейчас всегда `noreply@example.com`, если
  у клиента нет email (см. `buildReceiptBody` в `atol-provider.ts`) —
  часть провайдеров ОФД требует email или телефон в чеке; проверьте
  требования АТОЛ, если чек не проходит валидацию.
