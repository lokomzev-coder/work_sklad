# Публичный REST API — обзор

Блок O: первый публичный REST API проекта. До этого всё общение с БД шло
только через Server Actions внутри самого Next.js-приложения (форма → action
→ redirect/revalidate) — снаружи достучаться было нельзя. Теперь есть
`/api/v1/entity/{type}` для внешних интеграций (1С, BI-система, свой скрипт).

Конвенции (`meta`/пагинация/фильтрация/`expand`/формат ошибок) сознательно
списаны со стиля МойСклад JSON API 1.2 — если вы раньше писали интеграцию с
МойСклад, паттерны будут знакомы. **Имена сущностей и полей — свои**, не
скопированы буква в букву (`Order`, а не `customerorder`) — see
`entities.md` за кратким списком типов или **`reference.md` за полным
референсом**: таблица полей с типами по каждой сущности, что можно
писать/только читать, обязательные поля при создании, примеры `curl` на
чтение и создание.

## Авторизация

API-ключ на организацию, не привязан к логину/паролю конкретного
пользователя. Создать/отозвать — `Настройки → API-ключи` (только ADMIN).
Ключ показывается один раз при создании — в БД хранится только его хэш, при
утере ключ восстановить нельзя, только отозвать и создать новый.

```
Authorization: Bearer ewk_XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX
```

Ключ даёт **полный доступ ко всей организации** (эквивалент роли ADMIN) —
в этой версии нет скоупинга ключа по ресурсам/правам (например «только
чтение» или «только каталог») — это отдельная будущая доработка, не путайте
с ролевой моделью основного интерфейса (`lib/permissions.ts`), которая на
API-ключи не распространяется вообще.

## Базовый URL

```
https://ваш-домен/api/v1/entity/{type}
```

`{type}` — один из ключей реестра в `entities.md` (`client`, `order`,
`catalogItem` и т.д.).

## Список сущности

```
GET /api/v1/entity/client?limit=50&offset=0
```

Ответ:
```json
{
  "meta": { "size": 137, "limit": 50, "offset": 0, "nextHref": "...", "previousHref": null },
  "rows": [ { "id": "...", "name": "ООО Ромашка", ... }, ... ]
}
```

## Одна сущность

```
GET /api/v1/entity/client/{id}
```
```json
{ "meta": { "href": "https://.../api/v1/entity/client/abc123", "type": "client" }, "id": "abc123", "name": "..." }
```

## Создание / обновление / удаление

`POST /api/v1/entity/{type}` (создание), `PUT /api/v1/entity/{type}/{id}`
(частичное обновление — как в МойСклад: непереданные поля не трогаются),
`DELETE /api/v1/entity/{type}/{id}`.

**Работает не для всех типов.** Справочники (`client`, `employee`, `store`,
`contract`, `project`, `salesChannel`, `legalEntity`, `catalogItem`) —
полный CRUD. Документы (`order`, `purchaseOrder`, `stockMovement`,
`payment`, `invoiceOut`, `invoiceIn`) — **только чтение** в этой версии.

**Почему документы только для чтения**: у Order/StockMovement/Payment и
других документов настоящая бизнес-логика (нумерация, резервирование склада
`StockReservation`, FIFO-списание себестоимости, статус по умолчанию) живёт
в существующих Server Actions (`actions/orders.ts::upsertOrder`,
`actions/fulfillment.ts` и т.д.), которые сами читают сессию пользователя
(`getOrgContext`) — у запроса с API-ключом сессии нет. Голое
`prisma.order.create()` в обход этой логики создало бы формально валидную,
но бизнес-логически сломанную запись (без синхронизированного резерва,
без корректного статуса). Правильное решение — отрефакторить эти actions
так, чтобы принимать явный контекст (`{orgId, employeeId}`) вместо того,
чтобы всегда доставать его из сессии, и уже тогда дать API писать через тот
же код, что использует основной интерфейс. Это отдельная, более рискованная
задача (трогает проверенное ядро), не сделана в этой фазе — зафиксировано
как следующий шаг.

## Фильтрация / поиск / сортировка / expand

См. `errors-and-limits.md` за полным синтаксисом и примерами `curl`.

## Rate limiting

Свой in-memory лимитер на процесс (без Redis) — 45 запросов / 3 секунды на
ключ. См. `errors-and-limits.md`.

## Журнал изменений (audit log)

Каждое `create`/`update`/`delete` через этот API (для тех типов, где запись
вообще разрешена) автоматически пишет запись в журнал изменений —
`GET /api/v1/entity/auditLog` (только чтение) или
`Настройки → Журнал изменений` в интерфейсе. Запись содержит, кто (по
какому API-ключу), что именно изменилось (`diff`: `{поле: {from, to}}` для
`update`, полный снимок для `create`/`delete`), когда.

**Важная оговорка**: это надёжно работает **только для мутаций через сам
этот API** — изменения, сделанные из основного интерфейса (обычные
Server Actions), в этой версии в журнал **не** попадают. Причина —
техническая находка при реализации: используемый механизм
(`AsyncLocalStorage`) не переживает промежуточный запрос к БД между
моментом установки «кто действует» и самой мутацией — в интерфейсе почти
всегда есть хотя бы один такой промежуточный запрос (проверка прав,
валидация связанных записей), а в API-роутах после уточнения оказалось
достаточно устанавливать актёра непосредственно перед самим вызовом
`create`/`update`/`delete`. Подробности и возможные пути закрытия этого
пробела — комментарий в `src/lib/audit-context.ts` и `ROADMAP.md`, Блок O
фаза 3.

## Типы цен и скидки (`priceType`, `discount`)

Полный CRUD, полезны сами по себе (например, выгрузить прайс-лист для
внешней системы через `catalogItem?expand=prices`). **Не влияют на цену**,
которую фактически ставят Заказ/Розничная продажа/Счёт — там по-прежнему
всегда используется `catalogItem.unitPrice`, как и раньше. Причина —
подключение «этот канал продаж/клиент использует такой-то тип цены» или
«к этому товару применяется такая-то скидка» при оформлении документа —
это изменение самой логики ценообразования в оформлении заказа/кассы, не
просто новый справочник рядом с существующими данными; сделано осознанно
отдельно от этой фазы (см. `ROADMAP.md`, Блок O фаза 4, за подробным
обоснованием).

## Справочники, задачи, статьи расходов (`customEntityType`, `task`, `expenseItem`)

Полный CRUD. `customEntityType` — пользовательский справочник (МойСклад's
customentity), может стоять за полем «Справочник» в доп. полях сразу
нескольких сущностей (`Настройки → Доп. поля`) — сами значения справочника
(`CustomEntityValue`) управляются только через `customEntityType?expand=
values`, отдельного типа для них нет (тот же принцип, что у
`catalogItem?expand=prices` в фазе 4). `task` — ручная задача сотруднику
(`createdById`/`assignedEmployeeId` — настоящие внешние ключи на
`employee`, невалидный id вернёт `409`, а не тихо пройдёт). `expenseItem` —
пока просто справочник статей расходов, привязка к реальной расходной
операции появится в фазе 6 вместе с кассовыми ордерами вне розничной смены.

Комментарии к документам (МойСклад's eventfeed) **не** экспонированы через
этот API в этой версии — доступны только из интерфейса (карточки Заказа,
Заказа поставщику, Счетов, Складского движения, Производственного задания).
Причина: право комментировать документ завязано на право ПРОСМОТРА самого
документа (`actions/comments.ts`), а не на отдельное разрешение — у
API-ключа же в этой версии нет ресурсно-скоупированных прав вообще (см.
выше), так что этот механизм пока не переносится на API без более широкой
доработки скоупинга ключей.

## Кассовые ордера и корректировки баланса (`cashOrder`, `counterpartyAdjustment`, `priceList`)

`cashOrder` — приходный/расходный кассовый ордер вне розничной смены
(взнос учредителя, хоз. расходы) — полный CRUD, `counterpartyId`
необязателен (в отличие от обычного `payment`, где контрагент обязателен) —
именно это и было пробелом, который закрывает эта сущность. `expenseItemId`
осмыслен только для `direction: "OUT"`, категоризирует расход через
справочник `expenseItem`.

`counterpartyAdjustment` — ручная корректировка баланса контрагента
(прощение долга, перенос сальдо при миграции с другой системы) —
`side: "RECEIVABLE" | "PAYABLE"` выбирает, какой из двух независимых
балансов клиента (как покупателя/как поставщика) корректировать; `amount`
уменьшает выбранный баланс. Учитывается автоматически в `lib/balances.ts::
getClientBalance`, которую видно на карточке клиента в интерфейсе.

`pricelist` МойСклад **не реализован как отдельная API-сущность** —
прайс-лист в этом проекте не хранимый документ, а лёгкое сгенерированное
представление (`Настройки` → нет, `Каталог → Прайс-лист` в интерфейсе),
целиком производное от уже существующих `catalogItem`/`priceType` — своей
бизнес-логики или истории у него нет, поэтому не оправдывает отдельную
модель/API-тип; получить те же данные программно можно через
`catalogItem?expand=prices`.

## Изображения и файлы-вложения

Не экспонированы через этот API в этой версии — по той же причине, что и
комментарии (фаза 5): право на файл завязано на право просмотра того
документа/товара, к которому он прикреплён, а не на отдельный ресурс, а у
API-ключа в этой версии нет ресурсно-скоупированных прав вообще. Изображения
товара и файлы на документах доступны только из интерфейса — карточка
товара (галерея) и карточки Заказа/Заказа поставщику/Счетов/Складского
движения/Производственного задания (список файлов), там же и загружаются.

## Асинхронный экспорт (`?async=true`)

Для выгрузки ВСЕХ строк, подходящих под `filter`/`search`/`order` (не одной
страницы, как обычный `GET`), добавьте `?async=true` к списочному запросу:

```
GET /api/v1/entity/catalogItem?async=true&filter=status=ACTIVE
→ 202 { "id": "...", "status": "PENDING", "meta": { "href": ".../api/v1/export/{id}" } }

GET /api/v1/export/{id}
→ { "id": "...", "status": "DONE", "rows": [ ... ] }   (когда готово)
→ { "id": "...", "status": "FAILED", "error": "..." }  (если упало)
```

Результат — тот же формат строк, что у обычного списка (та же проекция
полей), просто целиком, без пагинации, и отдаётся не сразу, а по готовности.
Как и `registerFiscalReceipt` (Блок E/M3) — это НЕ настоящая очередь с
воркерами: задача создаётся и сразу же начинает обрабатываться в фоне того
же процесса. Для масштаба этого проекта разница между «сразу в фоне» и
«позже из очереди» не наблюдаема снаружи — настоящая очередь была бы
неоправданной сложностью, а не отсутствующей возможностью. Результат
хранится как JSON прямо в записи задачи (не файл) — оправдано объёмом
данных, с которым работает это приложение; не подходит для действительно
огромных выгрузок.

## Что дальше (не реализовано в этой фазе)

- Скоупинг ключа по ресурсам/правам (сейчас — всегда полный доступ).
- Запись для документов (см. выше).
- Вебхуки уже существуют отдельно от этого API (Блок M3,
  `Настройки → Вебхуки`) — не путать одно с другим, это разные механизмы
  (вебхук уведомляет вас о событии, этот API — вы сами запрашиваете данные).
