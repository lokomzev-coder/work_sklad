# Roadmap: путь к паритету с МойСклад

Живой документ. Обновляется по мере того, как меняются приоритеты и появляются
новые находки о болях клиентов МойСклад. Дерево сущностей МойСклад изучено по
исходникам их документации (`github.com/moysklad/api-remap-1.2-doc`, папка
`md/`) — таксономия ниже основана на нём, но мы **не копируем API 1:1**, а
переносим смысл в свою модель, в своём стиле (изумрудный, современный UI).

## Как читать этот документ

- **MVP (Фазы 0–8)** — то, что уже согласовано и частично реализовано в
  основном плане проекта. Не дублируется здесь подробно, см. историю чата.
- **Фазы 9+** — расширение до паритета с МойСклад, сгруппировано по доменным
  блокам в порядке приоритета. Каждый блок — это несколько недель работы, не
  один присест.
- Розница и производство — самые нишевые и объёмные блоки МойСклад. Пока не
  видно спроса от конкретных клиентов, они в самом низу очереди.

## Блок A — Товароучёт: ассортимент (после Фазы 4)

МойСклад различает `product` (товар), `service` (услуга), `bundle`
(комплект — набор из других товаров/услуг по фиксированной цене) и `variant`
(модификация товара — например, размер/цвет). У нас пока всё это одна модель
`CatalogItem`. Реальный товароучёт этого не выдержит надолго.

- **A1. Разделение CatalogItem** — `Product`, `Service`, `Bundle` как разные
  сущности (или единая таблица с discriminator + отдельные таблицы для
  специфичных полей — решить на месте по объёму полей).
- **A2. Группы товаров** (`productFolder`) — иерархия папок для каталога,
  аналог МойСкладовского `productFolder`.
- **A3. Модификации** (`variant`) — характеристики (`characteristic`, напр.
  "Размер", "Цвет") и сами варианты как дочерние записи товара со своим
  артикулом/штрихкодом/остатком.
- **A4. Единицы измерения** (`uom`) — штука, кг, м² и т.д., справочник +
  выбор на товаре (сейчас нет вообще).
- **A5. Штрихкоды** — базовое поле на товаре/варианте, без сканера пока.

## Блок B — Склады и остатки (после Блока A)

Это сердце МойСклад — без складского учёта система "как МойСклад" не
получится, у нас пока нет складов вообще.

- **B1. Склады** (`store`) — организация может иметь несколько складов.
- **B2. Остатки** — материализованный агрегат (или вычисляемый на лету)
  остатка товара по складу; источник истины — движения (см. B3).
- **B3. Документы движения**:
  - `enter` — оприходование (остаток появляется без документа закупки, напр.
    начальный ввод остатков)
  - `loss` — списание
  - `move` — перемещение между складами
  - `inventory` — инвентаризация (сверка фактического остатка)
- **B4. Отчёт "Остатки"** (`report_stock`) — таблица товар × склад × кол-во.

## Блок C — Документооборот закупок/продаж (после Блока B)

Сейчас `Order` — плоская сущность без статусной машины и без связи со
складом. МойСклад строит цепочки документов, где каждый шаг — отдельный
документ со своим влиянием на остатки/деньги.

- **C1. Расширение продаж**: `CustomerOrder` (запрос) → `Demand` (отгрузка,
  списывает остаток) → `SalesReturn` (возврат от клиента). Наш нынешний
  `Order` станет `CustomerOrder`, `Demand` — новая сущность.
- **C2. Закупки**: `PurchaseOrder` (заказ поставщику) → `Supply` (приёмка,
  прибавляет остаток) → `PurchaseReturn`.
- **C3. Счета и оплаты**: `InvoiceOut`/`InvoiceIn` (счета), `PaymentIn`/
  `PaymentOut` (оплаты), `Prepayment` (предоплата) — привязка к заказам,
  влияние на "баланс по контрагенту".
- **C4. Статусная машина документов** (`states`) — настраиваемые статусы
  (Новый/В работе/Отгружен/Оплачен...) вместо жёсткого enum.

## Блок D — Контрагенты и организация: расширение (можно параллельно с C)

- **D1. Организации** (`organization`) — юрлица самой компании (если их
  несколько — ИП + ООО и т.п.), документы выставляются от имени организации.
- **D2. Договоры** (`contract`) — привязка заказов/счетов к договору.
- **D3. Каналы продаж** (`saleschannel`) — розница/опт/маркетплейс — на
  заказе, для отчётности.
- **D4. Расширение Client**: несколько контактных лиц, несколько адресов,
  реквизиты (ИНН/КПП/ОГРН, банковские реквизиты) — сейчас только ИНН.

## Блок E — Розница (низкий приоритет, отдельный крупный блок)

Кассы и офлайн-точки продаж — целый отдельный интерфейс (кассир, а не
менеджер), не факт что нужен нашим клиентам. Не начинать без явного запроса.

- Точки продаж (`retailstore`), кассовые смены (`retailshift`), розничная
  продажа (`retaildemand`), внесение/изъятие наличных, розничный возврат.

## Блок F — Производство (низкий приоритет)

Технологические карты, этапы обработки, производственные задания
(`processingplan`, `processingstage`, `productionTask`) — нишевый блок для
компаний с собственным производством. Тоже не начинать без запроса.

## Блок G — Отчёты (после Блока C, по кусочкам)

- Остатки (см. B4), Обороты (`report_turnover`), Деньги (`report_money`),
  P&L (`report_pnl`), Продажи по заказам, Взаиморасчёты с контрагентом.
- Технически — агрегирующие SQL-запросы/представления поверх документов;
  реализовывать по одному отчёту за раз, начиная с "Остатков" и "Денег" как
  самых востребованных.

## Блок H — Сквозные возможности (по ходу, не отдельная фаза)

- Печатные формы документов (шаблоны, PDF) — понадобится рано или поздно
  почти в каждом блоке C.
- Мультивалютность (`currency`) и ставки налога (`taxrate`) — учитывать в
  моделях уже в блоке A/C, не переделывать потом.
- Пользовательские поля на сущностях (`customentity`-подобное) — обычно
  просят клиенты, у которых "почти всё подходит, но не хватает одного поля".
- Вебхуки — для будущих интеграций (1С, сайты, маркетплейсы).

## Принцип работы с этим роадмапом

1. MVP (Фазы 0–8) доводим до конца в любом случае — это база, без которой
   остальное не на чем строить (авторизация, роли, архивирование, паттерны
   UI).
2. Дальше — Блоки A → B → C → D в этом порядке: они прямо зависят друг от
   друга (нет смысла в документообороте продаж без складов, нет смысла в
   складах без нормального каталога).
3. Блоки E/F — только по явному запросу пользователя или после того как
   найдутся клиенты, которым это нужно ("изучать боли клиентов").
4. Отчёты (G) и сквозные штуки (H) — вкрапляются по ходу, не ждут отдельного
   "часа X".
