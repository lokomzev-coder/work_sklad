# Roadmap: путь к паритету с МойСклад

Живой документ. Обновляется по мере того, как меняются приоритеты и появляются
новые находки о болях клиентов МойСклад. Дерево сущностей МойСклад изучено по
исходникам их документации (`github.com/moysklad/api-remap-1.2-doc`, папка
`md/`) — таксономия ниже основана на нём, но мы **не копируем API 1:1**, а
переносим смысл в свою модель, в своём стиле (изумрудный, современный UI).

## Как читать этот документ

- **MVP (Фазы 0–8)** — то, что уже согласовано и частично реализовано в
  основном плане проекта. Не дублируется здесь подробно, см. историю чата.
- **Фазы 9+** — расширение до паритета с МойСклад, сгруппировано по доменным
  блокам в порядке приоритета. Каждый блок — это несколько недель работы, не
  один присест.
- Розница и производство — самые нишевые и объёмные блоки МойСклад. Пока не
  видно спроса от конкретных клиентов, они в самом низу очереди.

## Блок A — Товароучёт: ассортимент (после Фазы 4)

МойСклад различает `product` (товар), `service` (услуга), `bundle`
(комплект — набор из других товаров/услуг по фиксированной цене) и `variant`
(модификация товара — например, размер/цвет). У нас пока всё это одна модель
`CatalogItem`. Реальный товароучёт этого не выдержит надолго.

- ✅ **A1. Разделение CatalogItem** — решено единой таблицей с discriminator
  (`CatalogItemType`), а не раздельными таблицами: `PRODUCT`/`SERVICE` уже
  были так устроены, добавлять отдельные таблицы ради `BUNDLE` было бы
  избыточно. `BUNDLE` — тот же `CatalogItem` + join-таблица
  `CatalogItemComponent` (состав: другие товары/услуги с количеством, без
  вложенных комплектов — проверяется в `actions/catalog-bundles.ts`).
- ✅ **A2. Группы товаров** (`productFolder`) — иерархия папок для каталога
  (`CatalogGroup`, self-relation `parentId`), с защитой от циклов и запретом
  удаления непустой группы. ✅ Фильтр по группе на `/catalog` (точное
  совпадение группы, без подгрупп — расширить до "группа + все подгруппы"
  можно позже, если понадобится).
- ✅ **A3. Модификации** — `Characteristic` (справочник, напр. "Размер",
  "Цвет") + `CatalogItemVariant` (модификация PRODUCT-товара: свой
  артикул/штрихкод/цена-переопределение) + `CatalogItemVariantValue`
  (значения характеристик). **Сознательно БЕЗ отдельного остатка по
  варианту** — остаток по-прежнему считается только на уровне базового
  `CatalogItem` (см. Блок B); переработка леджера и всех потоков
  отгрузки/приёмки под гранулярность на уровне варианта — отдельная, более
  крупная задача, не тянули её в этот же заход. `OrderLineItem.variantId`
  позволяет заказать конкретную модификацию, цена снимается из
  `priceOverride` варианта (если задан), иначе из цены каталога.
- ✅ **A4. Единицы измерения** (`uom`) — справочник `Unit` (название +
  сокращение), выбор на `CatalogItem`.
- ✅ **A5. Штрихкоды** — поле `barcode` на `CatalogItem`, без сканера.

## Блок B — Склады и остатки ✅ (MVP-версия)

- ✅ **B1. Склады** (`Store`) — CRUD, архивируемые (без уничтожения истории
  движений — `onDelete: Restrict`).
- ✅ **B2. Остатки** — **не материализованы**, всегда вычисляются на лету из
  леджера движений (`lib/stock.ts::getStockBalances`, агрегирующий
  `$queryRaw` по `StockMovementLine`) — решено в пользу этого варианта
  явно то, чтобы остатки не могли разойтись с историей движений.
- ✅ **B3. Документы движения** — `StockMovement`/`StockMovementLine`,
  4 типа (`ENTER`/`LOSS`/`MOVE`/`INVENTORY`), **неизменяемые после создания**
  (ошибка исправляется новым корректирующим движением, а не правкой истории
  — как в бухгалтерии). `INVENTORY` считает знаковую дельту (факт − текущий
  остаток) на момент проведения.
- ✅ **B4. Отчёт "Остатки"** (`/warehouse/stock`) — таблица склад × товар ×
  количество.
- Только `PRODUCT` участвует в складском учёте — `SERVICE` не физический
  товар. ✅ Остаток `BUNDLE` — отдельная секция «Комплекты (доступно к
  сборке)» на `/warehouse/stock` (`lib/stock.ts::getBundleStockBalances`):
  не отдельный леджер, а на лету — для каждого склада минимум по всем
  компонентам от `floor(остаток компонента / нужно на 1 комплект)`. Строка
  не показывается, если результат 0 (тот же принцип, что у обычных
  остатков — нулевая доступность не несёт информации).

## Блок C — Документооборот закупок/продаж ✅ (MVP-версия)

- ✅ **C1. Расширение продаж**: `Order` остался как есть (это и есть
  `CustomerOrder`) + новый тип складского движения **`DEMAND`** (отгрузка) —
  решено НЕ заводить отдельные модели `Demand`/`Supply`, а расширить уже
  существующий `StockMovement`/`StockMovementLine` полями `orderId`/
  `purchaseOrderId` + `unitPriceSnapshot`. DEMAND ведёт себя как `LOSS`
  (списывает остаток), но привязан к заказу и снимает цену из строки заказа,
  а не из текущей цены каталога. Частичные/множественные отгрузки одного
  заказа поддержаны (`actions/fulfillment.ts::createDemand`), с защитой от
  превышения количества по заказу.
- ✅ **C2. Закупки**: новая модель `PurchaseOrder`/`PurchaseOrderLineItem`
  (зеркало `Order`, но поставщик = `Client`, цена вводится вручную —
  закупочная стоимость обычно не совпадает с ценой продажи) + тип движения
  **`SUPPLY`** (ведёт себя как `ENTER`), та же защита от избыточной приёмки.
  `Client` теперь используется в двух ролях (покупатель и поставщик) —
  отдельной модели `Supplier` сознательно не заводили.
- ✅ **C3. Платежи** (упрощённая версия) — модель `Payment` (`IN`/`OUT`,
  сумма, контрагент, опциональная привязка к заказу/заказу поставщику) +
  `lib/balances.ts::getClientBalance` (сколько должен нам / сколько должны
  ему). **Полноценные `InvoiceOut`/`InvoiceIn`/`Prepayment` как отдельные
  документы не реализованы** — сознательно урезано до минимального денежного
  леджера, этого достаточно для ответа "кто кому должен" без полноценного
  документооборота счетов.
- ✅ **C4. Настраиваемые статусы документов** — `DocumentStatus` (per-org,
  отдельные наборы для `ORDER`/`PURCHASE_ORDER`: название, цвет, порядок,
  флаг «финальный»), заменил жёсткие enum `OrderStatus`/`PurchaseOrderStatus`.
  Каждая организация получает 4 стандартных статуса при первом обращении
  (`lib/document-statuses.ts::ensureDefaultStatuses`, тот же паттерн
  ленивого бэкфилла, что у DEK вольта). UI — `/settings/statuses`
  (добавление/переименование/порядок стрелками/удаление, если статус не
  используется).
  ✅ **Граф переходов** (`DocumentStatusTransition`, по явному запросу) —
  опционально: пока для статуса не задано ни одного правила, из него можно
  перейти в любой другой статус того же вида документа (обратная
  совместимость — существующие организации ничего не замечают). Как только
  добавлено хотя бы одно правило «из X → в Y» — статус X становится
  ограничен: доступны только явно перечисленные переходы. У каждого правила
  необязательный список ролей (`Role[]`, пусто = доступно всем, у кого вообще
  есть право менять статус) — это дополнительное сужение поверх базовой
  проверки `assertPermission`/`orderScope`, не замена. Enforced и на сервере
  (`getAllowedNextStatusIds` в `actions/orders.ts`/`purchase-orders.ts`), и
  в UI (`getSelectableStatuses` — выпадающий список показывает только
  текущий статус + разрешённые следующие, а не все статусы вида документа).
  UI управления — там же на `/settings/statuses`, ниже списка статусов.
  Сознательно не сделано: причины отказа/автоматических действий на переходе
  (webhook на смену статуса уже есть отдельно) — не спрашивали.
- ✅ **SalesReturn / PurchaseReturn** — реализованы ровно так, как и
  предполагалось: два новых типа `StockMovementType`
  (`SALES_RETURN`/`PURCHASE_RETURN`), зеркальные DEMAND/SUPPLY. Возврат
  ограничен тем, что реально было отгружено/принято и ещё не возвращено
  (`actions/fulfillment.ts::createSalesReturn`/`createPurchaseReturn`).

**Расширение (тот же день, по явному запросу «довести до логики МойСклад»)**,
план `C:\Users\prokyrorrr\.claude\plans\jiggly-sprouting-flame.md` — исследование
показало, что у МойСклад **две разные системы производства** (см. Блок F2 ниже
про отложенную многоэтапную); решено расширить текущую одношаговую модель себестоимостью
и периферией, а граф этапов — отдельным блоком:

- **Себестоимость** — `TechCard.laborCost` (опционально, труд/накладные на
  партию) + `lib/production-cost.ts::getLastPurchaseUnitCosts` (себестоимость
  сырья = последний известный `unitPriceSnapshot` по движению `SUPPLY` этого
  товара в организации — тот же уровень точности, что и P&L, не FIFO/
  средневзвешенная). Материалы без истории закупок списываются по цене 0, с
  явным предупреждением в UI (`toast.warning`), а не молча. `completeProductionOrder`
  теперь пишет реальный `unitPriceSnapshot` на CONSUME- и OUTPUT-строки.
- **Проверка остатков** — `completeProductionOrder` блокирует проведение (не
  предупреждает), если сырья не хватает — по аналогии с защитой от
  превышения в `createDemand`.
- **Частичное выполнение** — новое поле `ProductionOrder.completedQuantity`
  (накопительно); `completeProductionOrder(orgSlug, id, partialQuantity?)`
  можно вызывать несколько раз, каждый раз посылая пропорциональную пару
  движений; `completedAt` выставляется только когда накопленное количество
  достигает `quantity`. Редактирование техкарты/склада блокируется после
  первого частичного проведения; блок «История выполнения» на карточке
  задания показывает каждую проводку отдельно (дата/количество/цена).
- **Отчёты**: `getPnlReport` — `costOfGoods` теперь включает стоимость
  произведённого товара (`PRODUCTION_OUTPUT`) наравне с закупленным
  (`SUPPLY`); `PRODUCTION_CONSUME` намеренно исключена (иначе двойной счёт —
  сырьё уже посчитано при закупке). `getTurnoverReport` — производственные
  движения раньше вообще не попадали в отчёт (не только не считалась
  себестоимость — сами количества не показывались), теперь `PRODUCTION_OUTPUT`
  считается приходом, `PRODUCTION_CONSUME` расходом.
- **Кастомные поля** — `CustomFieldEntityType.PRODUCTION_ORDER`, подключены на
  форме создания/редактирования и в статичной сводке уже выполненного
  задания (значения видны и после завершения, не только во время
  редактирования).
- **Вебхуки** — `PRODUCTION_ORDER_CREATED`/`PRODUCTION_ORDER_STATUS_CHANGED`
  (раньше не вызывался вовсе для статуса — починено попутно) /
  `PRODUCTION_ORDER_COMPLETED`.
- **Печатная форма** — `/print/production-orders/[org]/[id]`, новый компонент
  `PrintProductionDocument` (две таблицы — списано сырья / выпущено — вместо
  одной с контрагентом, которого у производства нет). До первой проводки
  показывает плановые цифры из техкарты без цены; после — фактические,
  агрегированные по товару **суммой реальной стоимости каждой проводки**, не
  количеством × цена последней проводки (первая версия агрегации была
  неверна при разных ценах между частичными выполнениями — исправлено при
  живой проверке).
- **CustomRole-скоуп** для `production` — независимый контрол от
  `ordersScope` (тот сейчас одним значением кормит `orders`+`purchaseOrders` —
  осознанный прецедент для похожих ролей продаж/закупок; цех — обычно другие
  люди, смешивать нельзя). `ProductionOrder.assignedEmployeeId` уже
  существовал, просто не было scope-проверки.

**Живой прогон через `@playwright/cli`** в изолированной org подтвердил весь
путь, включая денежную часть: техкарта «10 муки → 5 хлеба» с `laborCost=20` →
20 муки без истории цены (оприходование, не закупка) → задание на 10 хлеба →
частичное выполнение на 4 → списано 8 муки по 0.00 (нет истории, предупреждение
показано) + труд 16 → выпуск по 4.00/шт → закупка 100 муки по 8 ₽/шт (теперь
есть история) → довыполнение оставшихся 6 → списано 12 муки по 8.00, выпуск по
20.00/шт → `completedAt` проставлен → P&L: себестоимость 936 ₽ (800 закупка +
136 производство, без задвоения) → Обороты: мука приход 120/расход 20, хлеб
приход 10 — всё сошлось. Попытка выполнить задание на 1000 хлеба с 98 муки на
складе — заблокирована («Недостаточно остатка сырья»). При проверке найдены и
исправлены два реальных бага: (1) поле частичного количества не сбрасывалось
на новый остаток после успешного проведения — переведено на паттерн
override-до-следующего-ввода; (2) агрегация в печатной форме считала
`количество × цена последней проводки` вместо суммы реальной стоимости каждой
— искажало итог при разных ценах между частичными выполнениями.

**Сознательно не входит и в это расширение**:
- Многоэтапная обработка — см. Блок F2 ниже, отдельный крупный заход.

## Блок F2 — Многоэтапное производство ✅ (реализовано по явному запросу 2026-08-30)

МойСклад использует **две разные системы производства**, обе живые в API 1.2
(изучено по `github.com/moysklad/api-remap-1.2-doc`): старую одношаговую
(`processingplan`/`processingorder`/`processing` — Блок F выше) и современную
многоэтапную (`processingprocess`/`processingstage`/`productionstage`/
`productionstagecompletion`). Пользователь явно запросил вторую, назвав три
конкретных пробела: раздельные склад материалов/склад продукции, граф этапов,
техпроцессы с прямой зависимостью от техкарт. Реализовано по плану
`C:\Users\prokyrorrr\.claude\plans\jiggly-sprouting-flame.md`, с одной
сознательной урезкой относительно настоящего МойСклад (см. ниже).

### Что реализовано

- **`ProcessingStage`** (Этап производства) — переиспользуемый мастер-шаблон
  (name + опциональная `standardHourCost`), CRUD на `/production/stages`.
- **`TechProcess`** + **`TechProcessPosition`** (Техпроцесс) — именованная
  **линейная** последовательность этапов (не граф — см. «Сознательная
  урезка» ниже), CRUD на `/production/tech-processes` с up/down переупорядо­
  чиванием строк.
- **`TechCard.techProcessId`** (nullable) — прямая зависимость техкарты от
  техпроцесса, как и просил пользователь. `TechCardComponent.
  techProcessPositionId` (nullable) — материал привязан к конкретному этапу;
  без явной привязки при наличии техпроцесса материал относится к первому
  этапу (то же правило, что в МойСклад).
- **`ProductionOrder.materialsStoreId` + `.productsStoreId`** заменили
  единственный `storeId` — раздельные склад списания сырья и склад
  оприходования готовой продукции. `StockMovement` не потребовал изменений:
  у него и так один склад на движение, `PRODUCTION_CONSUME` просто теперь
  берёт `materialsStoreId`, `PRODUCTION_OUTPUT` — `productsStoreId`.
- **`ProductionStage`** (авто-генерируется по одной на позицию техпроцесса
  при создании задания на многоэтапную техкарту) + **`ProductionStageCompletion`**
  (журнал частичных выполнений одного этапа). `availableQuantity`/
  `blockedQuantity` **не хранятся**, вычисляются на лету
  (`lib/production-stages.ts::computeStageProgress`) из `totalQuantity`/
  `completedQuantity` текущего и предыдущего этапа — меньше поверхности для
  рассинхрона, чем денормализованные поля МойСклад.
- **`completeProductionStage`** — новый серверный экшен: списывает материалы
  только этой позиции техпроцесса (себестоимость — тот же
  `lib/production-cost.ts`, что у Блока F1), выпускает готовую продукцию
  **только если это последний этап** (как в МойСклад — промежуточные этапы
  только списывают, ничего не выпускают). Доступное количество валидируется
  **на сервере** через `computeStageProgress`, не только в UI.
- **`completeProductionOrder`** (Блок F1) остался нетронутым для техкарт БЕЗ
  техпроцесса — полная обратная совместимость; для техкарты С техпроцессом
  теперь возвращает ошибку с указанием выполнять по этапам.
- UI: `ProductionStagesPanel` на карточке задания (вместо плоской панели
  выполнения — рендерится, только если у техкарты есть техпроцесс), с
  прогрессом/блокировкой по каждому этапу и полем частичного выполнения.

### Сознательная урезка относительно настоящего МойСклад

- **Граф этапов → линейная последовательность.** У МойСклад
  `processingprocess.positions[].nextPositions` — граф с ветвлением. Малое/
  среднее производство почти всегда линейно; полный DAG (топологическая
  сортировка, множественные родители, циклы) — большая сложность ради
  возможности, которая вряд ли понадобится. Задокументировано явно, не
  спрятано.
- **`costDistributionType BY_PRICE`/`BY_PRODUCTION`** не перенесён — актуален
  только при нескольких выходных товарах с одного этапа; `TechCard.
  outputItemId` по-прежнему один, как в Блоке F1.
- **Ограничения исполнителей на уровне этапа** (`allPerformers`/`performers`
  у `processingstage`) не перенесены — переиспользуется уже существующий
  `CustomRole.production`-скоуп на уровне всего задания, не по этапам.

### Проверка

`npx tsc --noEmit`, `npm run lint`, `npm run build` — чисто. Миграция данных
(`ProductionOrder.storeId` → `materialsStoreId`/`productsStoreId`) сделана в
два прохода `db push` с backfill между ними, чтобы не потерять данные
существующих тестовых заданий; финальный дата-лосс-шаг (удаление старой
колонки) потребовал явного подтверждения пользователя — Prisma сама
заблокировала AI-агента от выполнения без него (см. `chat_history.md`,
раздел 58).

**Живой прогон через `@playwright/cli`** в `prod-check-qa`: 2 этапа («Замес»,
«Выпечка») → техпроцесс из них → техкарта «Хлеб многоэтапный» (техпроцесс +
мука привязана к «Замес») → задание на 10 хлеба, склад материалов «Основной
склад» ≠ склад продукции «Склад готовой продукции» → частичное выполнение
«Замес» на 4 → «Выпечка» **корректно заблокирована** (доступно 4, заблокировано
6 — ровно столько, сколько ещё не прошло «Замес») → выполнение «Выпечка» на 4
→ продукция ушла именно на «Склад готовой продукции», не на склад материалов
→ довыполнение обоих этапов до 10/10 → `completedAt` проставлен → регрессии на
старых одношаговых заданиях нет (проверено вживую).

При этом найден и исправлен **реальный баг себестоимости**: выпуск финального
этапа считал стоимость только из материалов, списанных НА САМОМ финальном
этапе — но в типичном рецепте сырьё расходуется на РАННИХ этапах («Замес»), а
не на финальном («Выпечка»), так что вся стоимость муки терялась (выпуск
считался по 0.00 вместо реальной цены). Это не была частная особенность
тестового сценария — так вело бы себя почти любое реалистичное многоэтапное
производство. Исправлено: перед постановкой выпуска суммируется вся
неатрибутированная стоимость материалов по всей истории заказа (все проводки
`PRODUCTION_CONSUME` минус уже учтённая в прошлых `PRODUCTION_OUTPUT`), тот же
уровень точности (взвешенное среднее, не FIFO), что уже принят в проекте.
Проверено повторным прогоном — себестоимость выпуска сошлась (160 ₽ мука на
10 хлеба → 26.67 ₽/шт на оставшиеся 6, после того как первая партия из 4 уже
разошлась по 0.00 до фикса).

## Блок F3 — Отдельный интерфейс производства, роль «Производство» ✅ (реализовано по явному запросу 2026-08-31)

Как в МойСклад: сотрудник с ролью «производство» должен получать доступ
ТОЛЬКО к производственному интерфейсу (задания/этапы), не видеть остальной
дашборд (клиентов/каталог/заказы/настройки).

**Гэп в текущей архитектуре** (проверено по коду): базовая роль `EMPLOYEE` в
`CAPABILITIES` (`lib/permissions.ts`) имеет `production: "read"`, а
`completeProductionOrder`/`completeProductionStage` требуют `"edit"` — то
есть сейчас **ни одна роль ниже `MANAGER` не может фактически выполнять
производство**. `CustomRole.permissions` умеет только сужать `scope`
(OWN/ALL) для 3 ресурсов, не выдавать доступ сверх базовой `Role` — сделать
«только production:edit, всё остальное none» через `CustomRole` сейчас
архитектурно нельзя (это требует полной ролевой матрицы, см. Итоги ниже,
отдельная большая переделка ~40 call sites).

**План (минимальный путь, без переделки всей ролевой матрицы)**:
1. Новое значение `Role` enum — `PRODUCTION` (третий базовый уровень наравне
   с `ADMIN`/`MANAGER`/`EMPLOYEE`).
2. `CAPABILITIES.PRODUCTION` в `lib/permissions.ts`: `production: "full"`,
   `catalog: "read"` (видеть техкарты/товары), `warehouse: "read"` (остатки
   при выполнении), всё остальное `"none"`.
3. Новая route-group `(dashboard)/[org]/floor/**` — упрощённый touch-friendly
   layout без обычного сайдбара, только список заданий/этапов (по
   `productionScope`, как сейчас) + кнопки выполнения этапа.
4. Гейт в layout обычного дашборда: `role === "PRODUCTION"` →
   `redirect(/floor)`; и наоборот, `/floor/**` редиректит прочь пользователей
   с другими ролями. `/org-select` — если у пользователя единственное
   членство с ролью `PRODUCTION`, сразу вести на `/floor`.

**Архитектурный вопрос решён** в пользу изолированной route-group в этом же
приложении (не буквально отдельный деплой) — дешевле в разработке/поддержке,
эквивалентно по ощущениям работника цеха. Легко переиграть на отдельный
деплой позже, если понадобится (роль/права уже отделены от роутинга).

### Реализация

`Role` enum получил значение `PRODUCTION` (`prisma db push`); `CAPABILITIES.
PRODUCTION` в `lib/permissions.ts` — `production: "edit"` (не `"full"` —
единственный уровень, который реально проверяют все production-экшены),

## Блок G2 — Расширенная аналитика и графики (по явному запросу, не начато)

Пользователь явно попросил добавить в план "подробные отчётности, графики по
всем возможным тонкостям" — зафиксировано отдельным блоком, **ждёт
реализации, не начат**.

Блок G даёт только табличные срезы за период одним агрегатом — ни
визуализации, ни разбивки по измерениям (сотрудник/канал/группа), ни
динамики во времени. Библиотека графиков в проекте не подключена
(`recharts` и аналоги отсутствуют в `package.json`) — потребуется выбрать и
подключить с нуля.

- **Графики динамики** поверх уже существующих отчётов (обороты, деньги,
  P&L) — линия/столбцы по дням/неделям/месяцам, а не одно число за весь
  период, как сейчас.
- **Сравнение периодов** — текущий период vs предыдущий, год к году — по
  всем денежным отчётам.
- **Разбивки продаж по измерениям** — по сотруднику (кто продал), по каналу
  продаж (`SalesChannel`), по группе каталога (`CatalogGroup`). Сейчас есть
  только "Продажи по клиентам" целиком, без графика и без других разрезов.
- **ABC-анализ** — товаров (по выручке/обороту) и клиентов (по
  обороту/задолженности), классификация A/B/C по вкладу в накопленный итог.
- **Топ-N** — топ товаров, топ клиентов, топ сотрудников за период.
- **Оборачиваемость склада** — среднее время от прихода до расхода по
  товару/группе (нет вообще сейчас).
- **Воронка статусов документов** — сколько заказов/ЗП в каждом статусе
  прямо сейчас, конверсия между статусами за период (используя граф
  переходов из C4 как структуру, но сам расчёт конверсии — новая логика).
- **Технически**: выбор библиотеки графиков (вероятно `recharts` — под него
  у shadcn/ui есть готовые `chart`-компоненты, логично ложится на уже
  используемый design system) + новые агрегирующие запросы в
  `lib/reports.ts` с группировкой по периоду/измерению (потребует
  `$queryRaw` с `date_trunc`, как уже делается в `lib/stock.ts`).

**Не начинать одним гигантским заходом** — "по всем возможным тонкостям"
крупная формулировка, список выше её конкретизирует, но при реализации
разумно двигаться по частям (например: сначала графики динамики поверх
существующих 4 отчётов → потом ABC/топ-N → потом разбивки по измерениям →
воронка статусов последней, она самая новая по логике).

  клиентам`) и в `lib/balances.ts::getClientBalance`. UI —
  `/settings/currencies`. **Упрощение**: используется последний известный
  курс валюты, а не курс на дату конкретной операции (`ExchangeRate.
  effectiveAt` хранится, но не используется как исторический lookup) — тот
  же уровень точности, что и у P&L (см. Блок G). Ставки налога (`taxrate`)
  не реализованы — не запрашивались.
- ✅ **H3. Пользовательские поля** — `CustomFieldDefinition`/
  `CustomFieldValue` (EAV, без FK на целевую строку — Prisma не умеет
  полиморфные связи, поэтому `archiveOrDelete` явно чистит значения при
  жёстком удалении Client/CatalogItem). Типы: текст/число/дата/да-нет/список.
  UI управления — `/settings/custom-fields`, подключено на все 4 сущности:
  Клиенты, Каталог, **Заказы и Заказы поставщику** (эти два — через
  `CustomFieldsEditor`, контролируемый вариант поверх React-состояния, а не
  `<form action>`, потому что формы заказов сами вызывают Server Action
  напрямую с JS-объектом, а не сабмитят нативную форму; `lib/custom-fields.ts`
  получил `saveCustomFieldValuesRecord` — тот же upsert-код, что и у
  FormData-варианта, но принимает `Record<string, string>`).
- ✅ **H4. Вебхуки** — `Webhook`/`WebhookDelivery`, HMAC-SHA256 подпись
  (`X-EasyWork-Signature`), события `ORDER_CREATED`/`ORDER_STATUS_CHANGED`/
  `PURCHASE_ORDER_CREATED`/`PURCHASE_ORDER_STATUS_CHANGED`/`PAYMENT_CREATED`.
  `lib/webhooks.ts::dispatchWebhookEvent` — fire-and-forget (не await'ится
  вызывающим действием, чтобы медленный/недоступный эндпоинт не подвешивал
  сохранение заказа), лог попытки (успех/код/ошибка) — в `WebhookDelivery`,
  видно на `/settings/webhooks`. **Нет очереди повторов** — недоставленное
  не ретраится автоматически (нет инфраструктуры фоновых задач в проекте).
- ⬜ **H5. Иконки валют на дашборде** (план, не начато, по явному запросу
  2026-08-31) — KPI-карточки с деньгами (`(dashboard)/[org]/page.tsx`,
  `reports/overview/page.tsx`) сейчас всегда используют иконку `DollarSign`
  из lucide-react, независимо от `Organization.baseCurrency`. План: новый
  `lib/currency-icons.ts` — маппинг код валюты → lucide-иконка
  (`RussianRuble`/`DollarSign`/`Euro`/`PoundSterling`/`JapaneseYen`/
  `SwissFranc`, все уже есть в установленной версии lucide-react; фолбэк
  `Coins` для нераспознанного кода, т.к. `currency` — свободная строка, не
  ISO 4217-валидируемая, см. `lib/format.ts`). Заменить `icon={DollarSign}`
  на `icon={getCurrencyIcon(baseCurrency)}` в этих 2 местах. Сложность:
  тривиальная (1 новый файл + 2 правки), готово к реализации в любой момент.

## Блок I — Сотрудники «как в МойСклад»: гибкие права и личный кабинет ✅ (сужено)

Реализовано по явному запросу, но **осознанно сужено** относительно
исследованной модели МойСклад (см. ниже) — полная матрица прав по каждой
сущности со scope `OWN_GROUP`/`OWN_GROUP_SHARED` не реализована, только то,
что реально запрашивалось: сотрудник видит только свои заказы.

### Что реализовано

- **`CustomRole`** (per-org, переиспользуемая) — `permissions` JSON вида
  `{ orders: { scope: "ALL" | "OWN" } }`. **Не замена булевой матрицы**, как
  изначально предполагалось в проекте — базовый enum `Role`
  (ADMIN/MANAGER/EMPLOYEE) по-прежнему решает, какие разделы вообще доступны
  (`lib/permissions.ts::can`/`assertPermission`, без изменений); `CustomRole`
  умеет только **сузить** видимость заказов до своих, когда назначена
  `Membership.customRoleId`. Она не может расширить доступ сверх базовой
  роли. UI — `/settings/roles`.
- **`Membership.employeeId`** — связывает логин с конкретным `Employee`, это
  и есть "кто я" для scope `OWN` (`Order.assignedEmployeeId === ctx.
  employeeId`). Резолвится заново на каждый запрос в `lib/tenant.ts::
  getOrgContext` (не кэшируется в JWT) — смена роли/scope администратором
  вступает в силу сразу, без ожидания обновления токена сессии сотрудника.
- **Личный кабинет сотрудника** — не отдельная оболочка приложения, а
  переиспользование уже существующего адаптивного UI (как и раньше скрывался
  пункт "Пароли" для EMPLOYEE): при scope `OWN` список `/orders` фильтруется
  по `assignedEmployeeId`, открыть чужой заказ по прямому URL — `404`
  (`orders/[id]/page.tsx`), `upsertOrder`/`updateOrderStatus` блокируют
  правку чужого заказа и принудительно проставляют `assignedEmployeeId =
  ctx.employeeId` при создании — сотрудник физически не может назначить
  заказ не на себя.
- **Выдача/отзыв личного доступа** — на карточке сотрудника, секция «Доступ
  в систему» (`actions/memberships.ts`, `EmployeeAccessSection`): логин +
  email + пароль (или переиспользование уже существующего `User` по email,
  если человек уже зарегистрирован в другой организации) + базовая роль +
  опциональная `CustomRole`. Отзыв удаляет только `Membership` — учётная
  запись `User` не удаляется (может состоять в других организациях).

### Сознательно не реализовано (из исследованной модели МойСклад)

- **Scope `OWN_GROUP`/`OWN_GROUP_SHARED`** — потребовал бы завести сущность
  "отдел", которой нет вообще; не запрашивалось, только `OWN`/`ALL`.
- **Матрица прав по ~50 сущностям × 6 действий** — `CustomRole` влияет только
  на `orders`, не на остальные ресурсы (`clients`/`catalog`/`vault`/...) —
  для них по-прежнему только базовая роль. Расширение `CustomRole` до полной
  матрицы означало бы переписать все ~40 мест, использующих
  `assertPermission(ctx.role, ...)`, по всему кодбейзу — непропорционально
  большой рефакторинг относительно того, что реально просили.
- ~~Аналогичный scope для `PurchaseOrder`~~ — реализован (см. ниже),
  зеркально `orders`: одно значение видимости в `CustomRole` теперь
  применяется к обоим ресурсам сразу (`{ orders: {scope}, purchaseOrders:
  {scope} }` — заполняются одинаково из единственного select'а в UI, отдельный
  контрол для заказов поставщику не заводили, раз никто не просил различать).
  `getOrgContext` резолвит `ctx.purchaseOrderScope` так же, как `orderScope`;
  `assertOwnPurchaseOrderScope` в `actions/purchase-orders.ts` зеркалит
  `assertOwnOrderScope`; список и карточка заказа поставщику фильтруют/404
  так же, как заказы.
- Дашборд-виджет «Последние заказы» и сумма по заказам теперь тоже уважают
  `orderScope` — было замечено при визуальной проверке, что сотрудник с
  scope `OWN` видел чужие заказы в этом виджете (хотя открыть их всё равно не
  мог — 404). Исправлено.

Конспект исходного исследования модели МойСклад — ниже, для истории и на
случай, если понадобится реализовать полную матрицу прав позже:

- **Модель ролей МойСклад**: 6 типов — Владелец, Системный администратор,
  Кассир, Сотрудник производства, Пользовательская роль (`customrole`,
  переиспользуемый шаблон прав на несколько сотрудников), Индивидуальная роль
  (`individualrole`, персональная для одного сотрудника). Гибкие роли —
  только на тарифах Professional/Corporate, то есть это осознанно premium-
  фича, не базовая.
- **Права** = набор из ~30 глобальных булевых флагов (`viewDashboard`,
  `viewProductCostAndProfit`, `exportData` и т.п.) + матрица по ~50 типам
  сущностей × до 6 действий (`view/create/update/delete/print/approve`), где
  каждая ячейка матрицы — не просто вкл/выкл, а один из уровней видимости:
  `NO → OWN → OWN_SHARED → OWN_GROUP → OWN_GROUP_SHARED → ALL`. Это даёт
  нативную поддержку «сотрудник видит только свои документы» и «видит
  документы своего отдела» без отдельного кода на каждую сущность.
- **Группы/отделы** (`Group`) — плоская сущность, используется только как
  признак принадлежности для `OWN_GROUP`-уровней видимости, без вложенности.
- **Назначение роли сотруднику** — отдельная привязка `employee → role`, не
  часть самой карточки сотрудника.
- **Не подтверждено источником** (осталось неизвестным): делится ли один и
  тот же человек одним логином/паролем между разными аккаунтами МойСклад, или
  учётки всегда полностью раздельные. Не блокирует наш дизайн — мы уже решили
  иначе (см. ниже).

### Живая проверка в UI МойСклад (2026-08-29)

Конспект выше был построен по GitHub-документации API. 2026-08-29 модель
дополнительно проверена вживую на новом тестовом аккаунте МойСклад
(Сотрудники → Добавить сотрудника → «Настроить права»), без изменения
реальных данных аккаунта. Ниже — то, что подтвердилось и уточнилось; заменяет
неточности конспекта выше, а не дублирует его.

- **5 системных вариантов при создании сотрудника** (радио-кнопки на карточке,
  не 6, как в конспекте — «Кассир» из конспекта на практике называется
  иначе и это не отдельная системная роль, а один из пяти пунктов):
  1. **Владелец аккаунта** — только один на аккаунт, есть кнопка «Сделать
     владельцем» на карточке другого сотрудника для передачи.
  2. **Администратор** — безлимитный доступ, без матрицы.
  3. **Пользователь** — открывает кнопку «Настроить права» на полную матрицу
     (см. ниже). Внутри этого пункта есть **переключатель** в самой матрице:
     «Индивидуальные настройки» (правки применяются только к этому
     сотруднику) vs **«+ Роль»** — то же самое становится именованной,
     переиспользуемой сущностью с полями «Название роли» + кнопки «Сохранить
     роль» / «Удалить роль». Это и есть буквальная реализация
     `customrole`/`individualrole` из конспекта: роль — это просто
     **сохранённый снимок той же матрицы** под именем, не отдельная модель
     данных с другим UI.
  4. **Доступ только к точкам продаж** — сотрудник входит только в Кассу
     (POS), не в веб-версию. Это и есть «Кассир» из конспекта, названный
     иначе.
  5. **Сотрудник производства** — аналогично, доступ только в отдельный
     продукт «МойСклад Производство», не в основной веб-интерфейс.
- **Матрица прав организована по 14 вкладкам-разделам** (не плоский список
  ~50 сущностей): Моя компания, Закупки, Продажи, Товары, Маркировка, CRM,
  Склад, Деньги, Розница, Производство, Настройки, Обмен данными,
  Справочники, Задачи. Каждая вкладка — таблица «сущность × действия».
- **Действия варьируются по типу сущности**, а не фиксированы на 6 для всех:
  - Документы (Продажи/Закупки/Деньги/Склад/Розница): **Смотреть, Печатать,
    Создавать, Редактировать, Удалять, Проводить** (6 колонок). «Проводить»
    = буквально «approve» из конспекта — проведение документа (влияет на
    остатки/деньги), отдельно от простого создания/редактирования.
  - Справочники без сценария владения (Валюты, Единицы измерения, Страны,
    Ставки НДС): только **Создавать/Редактировать/Удалять** — колонка
    «Смотреть» задизейблена на значении «Все» (видимость нельзя ограничить,
    это общие для аккаунта данные).
  - Задачи: **другой набор** — Смотреть, Создавать, Выполнять, Редактировать,
    Удалять — и **свой, более узкий scope-enum**, не общий 6-уровневый (см.
    ниже). Это важно: **у МойСклад нет одного универсального enum уровней
    видимости на все сущности** — они per-domain.
  - Часть строк — просто одиночные булевы флаги без scope/действий вообще
    («Прибыльность», «Товары на реализации», «Воронка продаж»,
    «Юнит-экономика» на вкладке Продажи; «Остатки»/«Обороты» на Складе;
    «Движение денежных средств»/«Взаиморасчеты»/«Прибыли и убытки»/«Видеть
    остатки денег» на Деньгах).
- **Точные значения scope-enum для документов** (выпадающий список у
  «Смотреть»/«Редактировать»), подтверждён порядок и формулировки в русском
  UI — это то, что в конспекте было `NO/OWN/OWN_SHARED/OWN_GROUP/
  OWN_GROUP_SHARED/ALL`:
  1. Только свои
  2. Свои и общие
  3. Свои и отдела
  4. Свои, отдела и общие
  5. Все
  6. Нет
- **Scope-enum для задач — отдельный, трёхуровневый**: Нет / Созданные и
  назначенные / Все. Подтверждает вывод выше: scope не универсален, у каждой
  доменной группы сущностей свой набор уровней.
- **Отделы (`Group` из конспекта) — подтверждены как плоская сущность**,
  создаются прямо инлайн с карточки сотрудника (поле «Отдел» + иконка-
  карандаш → модалка «Отделы» с списком name-полей и «+ Отдел»). Без
  вложенности, без своего раздела в настройках — это буквально просто список
  строк-меток, к которым привязывается сотрудник.
- **Чувствительные финансовые права по умолчанию выключены** — это не было в
  конспекте, но важно для дизайна: у свежесозданного «Пользователя» на
  вкладке «Деньги» **«Начисления зарплаты» = Нет** (и от этого задизейблены
  все остальные колонки в той же строке) и **«Видеть остатки денег» =
  выключено**, при том что почти все остальные права на других вкладках по
  умолчанию стоят в «Все»/включено. То есть дефолт МойСклад — «открыто везде,
  кроме зарплаты и остатков денег в кассе/на счетах».
- **Глобальные булевы флаги (вкладка «Настройки»)** — короче списка ~30 из
  конспекта, реально нашлось 6: Управление подпиской, Отправлять почту,
  Видеть себестоимость/цену закупки/прибыль товаров, Редактировать документы
  закрытого периода, Редактировать шаблоны документов и отчётов, Редактировать
  курс валюты документа. (Остальные ~24 из первоначальной оценки могут быть на
  более высоких тарифах/в других разделах, не проверялось.)
- **Ключевые сущности-справочники, подтверждённые под нашими аналогами**:
  «Контрагенты» (= наши `Client`), «Заказы поставщикам»/«Заказы покупателей»
  (= наши `PurchaseOrder`/`Order`), «Товары и услуги» (= наш `Catalog`).
  Дополнительно всплыли «Проекты» и «Каналы продаж» как отдельные
  справочники — сущностей, которых у нас пока нет вообще (см. открытый
  вопрос ниже).
- **Управление ролями — не отдельная страница**, только диалог «Настройка
  доступа» на карточке сотрудника; сохранённые роли показываются в том же
  выпадающем списке («Индивидуальные настройки» / имя роли / «+ Роль»,
  выбором вместо переключения) при повторном открытии для другого
  сотрудника — списка всех ролей аккаунта отдельным экраном в этом заходе не
  найдено (не факт, что его нет — не искали специально).

**Вывод для нашей архитектуры**: наш текущий `CustomRole` (единственное поле
`{ orders: { scope }, purchaseOrders: { scope } }`, OWN/ALL) — это
осознанно урезанный частный случай этой модели, а не другая архитектура.
Путь до паритета не требует смены подхода, только расширения: (1) добавить
`Group`-сущность (плоскую, как в МойСклад) для `OWN_GROUP`-уровней, (2)
превратить `CustomRole.permissions` из `{ orders, purchaseOrders }` в
таблицу «сущность → { view: scope, create: bool, edit: scope, delete: bool,
...}» по мере того, как для каждой сущности реально понадобится сузить
доступ — не переписывать всё разом. Само разделение «Индивидуальные
настройки vs именованная Роль» уже есть у нас в похожем виде (роль
опциональна на `Membership`), просто без UI-переключателя «сохранить как
роль» — это можно добавить дёшево, когда до этого дойдёт очередь.

### Как это ложилось на архитектуру (первоначальный план, во многом сбылось)

- **Личный вход сотрудника** — база уже есть: `Membership.login` +
  `login@orgSlug` (реализовано, см. `chat_history.md` раздел 34). Не хватает
  только UI «личного кабинета» с урезанной навигацией под роль сотрудника.
- **Scope-права по аналогии с МойСклад** — вместо булевой матрицы
  `lib/permissions.ts` (сейчас: роль → сущность → действие → true/false)
  добавить уровень `scope` (`OWN | OWN_GROUP | ALL`) к записям матрицы для
  сущностей, где это осмысленно (заказы, заказы поставщику — не для
  сотрудников/клиентов-справочников). Потребует: поле "ответственный/автор"
  уже есть на `Order` (`assignedEmployeeId`) — можно переиспользовать для
  `OWN`; для `OWN_GROUP` понадобится завести `Group`-подобную сущность
  (отдел), которой сейчас нет вообще.
- **Пользовательские/индивидуальные роли** — вместо enum `Role`, завести
  таблицу `CustomRole` (per-org, переиспользуемая) + опционально
  персональные права поверх неё на конкретного `Membership`. Существующий
  enum `Role` (ADMIN/MANAGER/EMPLOYEE) можно оставить как 3 предустановленных
  шаблона по умолчанию, не ломая текущую логику при миграции.
- **Масштаб задачи**: это не аддитивное расширение, как большинство прошлых
  блоков — `lib/permissions.ts` и все вызовы `can()`/`assertPermission()` по
  всему кодбейзу придётся переработать под scope-модель. Требует отдельного
  захода, не смешивать с другими блоками. Начинать только по явному запросу
  пользователя (как и Блоки E/F) — это premium-фича даже у эталона, не
  ожидаем спроса на неё на раннем этапе.

### I2.1 — Полная ролевая матрица (как в МойСклад) ✅ (реализовано 2026-08-31)

Реализовано целиком, по явному запросу пользователя (максимальная глубина
по всем трём осям, подтверждено через явный выбор при планировании — не
поэтапно «по одному ресурсу», как изначально осторожно рекомендовалось).

**Схема**: `Group` (плоский отдел, per-org) + `Employee.groupId`;
`Client.assignedEmployeeId` (новое — раньше у Client не было владельца
вообще, в отличие от Order/PurchaseOrder/ProductionOrder); `CustomRole.
isIndividual` (индивидуальные vs именованные роли).

**Движок** (`src/lib/permissions.ts`, полностью переписан): 9 старых грубых
ресурсов → **22 гранулярных** (orders/purchaseOrders/contracts/payments/
salesChannels — раньше все под одним `orders`; techCards/techProcesses/
productionOrders — раньше `production`; documentStatuses/customFields/
webhooks/legalEntities/exchangeRates/customRoles — раньше `settings`; плюс
новые `dashboard`/`reports`, которые раньше были вообще без гейта — видны
любому члену организации). Каждый ресурс — 4 независимых действия
(`view`/`create`/`edit`/`delete`), `view`/`edit` — scope-ранжированные
(`NONE < OWN < OWN_GROUP < ALL`, реально применимо только к 4 ресурсам с
владельцем — orders/purchaseOrders/productionOrders/clients). **Изменён
принцип**: раньше CustomRole мог только *сужать* базовую Role; теперь —
если роль назначена, она *авторитетна* по каждому явно заданному ресурсу
(может расширить или сузить), а не заданные ресурсы наследуют базовую Role.
Два ресурса — `membership`/`customRoles` — **никогда** не переопределяются
через CustomRole (жёсткий потолок против самоэскалации), плюс серверная
проверка «нельзя сохранить в роли права выше своих собственных».

**Миграция**: аудит нашёл **130 точек проверки** по всему кодбейзу.
Стратегия — ratchet через legacy-шим (`permissions-legacy.ts`, снэпшот
старого движка), а не big-bang: все точки сначала механически
переключены на шим (`tsc` чист, поведение не изменилось), затем мигрированы
**группами ресурсов** (часть — параллельными агентами, часть — вручную для
чувствительных groups), с сужением `ResourceLegacy`-юниона после каждой
группы (забытая точка = ошибка компиляции, не тихий пробел). После полной
миграции шим удалён целиком.

**Попутно найден и закрыт реальный гэп**: у большинства списков (orders,
clients, warehouse, production, employees, purchase-orders, contracts,
payments) не было view-гейта вообще — страницы рендерили полный список
всегда, `can()` использовался только чтобы прятать кнопку «Создать». Было
безопасно, пока роль не могла получить `NONE` через CustomRole — стало
дырой. Добавлены `notFound()`-гейты на все такие страницы + на 3 печатные
формы (`(print)/**`, были вообще без проверки прав, вне layout'а дашборда).

**Scope-резолюция** (новый `src/lib/scope.ts`): `assertRowScope`
(mutation-гвард на одну запись), `buildScopeWhere` (list-страницы),
`isRowVisible` (detail-страницы, `notFound()` вместо throw),
`resolveGroupMemberIds` (мемоизирован через React `cache()` — единственный
доп. запрос во всей системе, только при реальном использовании
`OWN_GROUP`). Заменяет 3 копипастных `assertOwnOrderScope`/
`assertOwnProductionScope`/`assertOwnPurchaseOrderScope`.

**UI**: `/settings/roles` (список именованных ролей — раньше без
редактирования вообще, только создать/удалить) + `/settings/roles/[id]`
(полный редактор матрицы, сгруппированный по 8 разделам как нав меню) +

сотрудника — новое поле «Отдел» (тот же паттерн, что «Склад по умолчанию»
из I2.2) + 3-позиционный переключатель «Базовая роль / Именная роль /
Индивидуальные настройки» (индивидуальный режим — скрытая
`CustomRole{isIndividual:true}` на одного сотрудника, редактируется на

именной» — просто снятие флага, без копирования данных); `sidebar-shell.tsx`

**Живая проверка** (`@playwright/cli`, org `f3-role-test`): создана роль с

### I2.5 — Создание сотрудника и выдача доступа одним шагом ✅ (реализовано 2026-09-01)

По жалобе пользователя: раньше `/employees/new` создавала только карточку
сотрудника — чтобы выдать логин/пароль/роль, нужно было отдельно зайти на
карточку ещё раз («сначала часть какая настраивается надо создать
сотрудника, а потом еще раз зайди чтобы донастроить»). На `/employees/[id]`
(редактирование) обе формы уже были на одной странице (`EmployeeForm` +
`EmployeeAccessSection`) — не хватало именно создания.

**`EmployeeForm`** получил необязательный `children` — рендерится внутри
того же `<form>`, так что любые дополнительные поля попадают в тот же
`FormData` на сабмите (не отдельная форма/экшен, один сабмит на всё).

**Новый `NewEmployeeAccessFields`** (`components/employees/`) — чекбокс
«Выдать доступ в систему сразу» (включён по умолчанию) раскрывает
логин/email-для-входа/пароль/базовую роль/пользовательскую роль (те же
поля, что в `GrantAccessForm`, плюс «+ Новая роль» из I2.4) — рендерится
как `children` в `EmployeeForm` на `/employees/new`.

**`createEmployee`** (`actions/employees.ts`) теперь одной транзакцией
создаёт и `Employee`, и (если чекбокс включён) `User`+`Membership` —
сознательно упрощённая версия `grantEmployeeAccess`: только новый
пользователь (пароль обязателен), без ветки «привязать к уже
существующему User по email» — этот редкий кейс (пригласить в новую org
человека, уже зарегистрированного в другой) по-прежнему доступен через
карточку сотрудника после создания, как раньше. Редирект после создания —
теперь сразу на карточку нового сотрудника (`/employees/[id]`), не на
список, чтобы админ сразу видел результат.

**Живая проверка** (`@playwright/cli`, org `f3-role-test`): создан
сотрудник «Комбо Тест» с доступом в одном сабмите → редирект на его
карточку, доступ виден сразу → разлогин → **успешный вход** новым
логином/паролем, выданными на этапе создания → профиль подтверждает
личность («Комбо Тест», указанный email). `npx tsc --noEmit`/`npm run
lint` — чисто. По ходу проверки поймана паника Turbopack HMR (`Restore of
All for task ... failed`) — не связана с кодом (видно в логах, что
одновременно шла ручная работа пользователя в другой org `prok` на том же
dev-сервере), сервер сам восстановился за секунды.

## Блок J — Импорт из Excel (исследование 2026-08-29, не начато)

Изучено вживую по явному запросу пользователя (студия — новый тестовый
аккаунт МойСклад, без изменений в проекте): официальная документация
(`support.moysklad.ru`, статья «Создание товаров импортом из Excel»), три
официальных шаблона (простой/подробный/Казахстан, скачаны и распарсены
через `xlrd`), плюс реальный тестовый прогон мастера импорта с намеренно
проблемным файлом (дубль кода между двумя товарами) — чтобы увидеть
фактическое поведение при ошибке, а не только то, что написано в доке.

### Механика мастера импорта

1. **Загрузка** — XLS/XLSX/CSV, до 10 Мб, drag&drop или выбор файла.
   Кодировка определяется/выбирается отдельно (Windows-1251 / UTF-8 —
   видно в HTML `<select>` рядом с полем сопоставления).
2. **Поле «Искать»** — определяет, по какому полю МойСклад матчит СУЩЕСТВУЮЩИЕ
   записи при повторном импорте: Автоматически, По UUID (только при
   обновлении — недоступно при создании новых, UUID не назначается вручную),
   По коду, По наименованию, По внешнему коду, По штрихкоду (отдельно для
   каждого из 4 форматов: EAN13/EAN8/Code128/UPC), По артикулу.
3. **Сопоставление столбцов** — на каждый столбец файла назначается одно
   значение из **63 возможных целевых полей** (полный список ниже),
   независимо друг от друга; неразмеченный столбец = «Не загружать».
   Автоопределение по имени заголовка работает не всегда: в тесте столбец
   «Группа» из простого шаблона не был подхвачен автоматически (остался «Не
   загружать»), хотя остальные 6 столбцов сопоставились верно — сопоставление
   не полагается только на точное совпадение имени.
4. **Два чекбокса-модификатора**: «Я хочу обновить только существующие
   товары и НЕ СОЗДАВАТЬ НОВЫЕ» (чистый update-режим) и «Заменить
   существующие изображения».
5. **Выполнение — асинхронная фоновая задача**, с уведомлением в колокольчике
   и отдельным экраном истории (Настройки компании → Обмен данными → Импорт):
   таблица всех прошлых запусков (создана/завершена/статус), с итогом вида
   «Обработано N строк, создано X, обновлено Y, Z строк пропущено из-за
   ошибок», и три ссылки на файл/подробности: **Подробнее** (модалка с
   построчным логом ошибок), **Лог задачи (файл)**, **Необработанные строки
   (файл)** — то есть неудачные строки можно скачать отдельно и
   переимпортировать после исправления. Задачи старше 10 дней удаляются
   автоматически; есть кнопка «Удалить завершённые задачи».
6. **Проверенное поведение при дубле ключа сопоставления внутри одного
   файла** — важное расхождение с формулировкой доки. Дока предупреждает:
   «убедитесь что значения уникальны, иначе товар многократно перезапишется»
   (звучит как overwrite). Фактически в тесте (2 строки с одинаковым «Код»
   в одном файле, поле поиска = Автоматически) вторая строка была не
   перезаписана, а **отклонена** с ошибкой `Запись уже импортирована`,
   первая строка создалась нормально. То есть defensive-поведение лучше, чем
   буквально написано в доке — стоит унести это же поведение в свою
   реализацию (rejected duplicate, не silent overwrite).

### Специальные форматы значений в столбцах (подтверждено шаблоном и текстом доки)

- **Группа/категория товара — путь через `/`**: `Сезонные/Ягоды`,
  `Одежда/Зимняя` — при импорте **автоматически создаётся вся недостающая
  цепочка вложенных групп** (проверено вживую: импорт с `Сезонные/Ягоды` +
  `Сезонные/Овощи` создал родителя «Сезонные» и обе подгруппы одним
  прогоном). Это **отдельная сущность от «Отделов» сотрудников** выше по
  документу — товарные «Группы» вложенные (дерево), сотрудничьи «Отделы»
  плоские; не путать, у МойСклад это два разных объекта с похожими ролями.
- **Модификации — не отдельный импорт, а строки с `Тип = Модификация`** в
  том же файле, привязанные к родителю через **«Код товара модификации»**
  (= значение «Код» родительской строки-товара). Значения характеристик
  модификации (цвет, эко-статус и т.п.) идут в динамически именованных
  столбцах `Характеристика:<Имя>` — каждая уникальная характеристика получает
  свой столбец.
- **Упаковки** — столбцы `Упаковка:<Имя>` (количество базовых единиц в
  упаковке) и опционально `Упаковка(ШК):<Имя>:<тип штрихкода>` (штрихкод
  именно этой упаковки, не товара). На шаге сопоставления столбцов выбирается
  спец-значение «Упаковка:Новая» / «Упаковка(ШК):Новая».
  Комплекты (`Тип = Комплект`) — импортом **нельзя ни создать, ни изменить
  состав**, только обновить характеристики (цену, страну и т.п.) уже
  существующего комплекта.
- **НДС** — число без «%» (или литерал «без НДС»); можно указать на строке
  Группы — тогда применяется ко всем товарам этой группы (группа как
  контейнер дефолтов, не только видимости).
- **Изображения** — прямые URL, несколько через `;` в одном столбце.
- **Групповые «карточки контента»** (для площадок/каналов онлайн-продаж) и
  **маркированная продукция** (специфичные для категорий вроде «Одежда»
  поля: ТН ВЭД, Целевой пол, Тип производства — обязательная маркировка
  «Честный знак») — тоже поддержаны отдельными наборами столбцов, не
  разбирались в деталях (не входило в заявленный приоритет).

## Блок K — Бизнес-процессы, сценарии-автоматизации, цепочка «Создать документ» (исследование 2026-08-29, не начато)

Продолжение исследования того же дня, вживую в тестовом аккаунте. Три
отдельных, но связанных механизма — все относятся к «гибким настройкам»,
которые пользователь просил изучить, но ни один не входит в матрицу прав из
Блока I (та матрица — про видимость/CRUD, эти три — про **workflow**: кто
может двигать документ по каким статусам, что происходит автоматически, и как
документы физически связаны друг с другом).

### 1. Бизнес-процессы — конструктор статус-переходов per-тип-документа

У каждого типа документа (Заказы покупателей, Заказы поставщику, ...) — свой
редактируемый бизнес-процесс (`Продажи → Заказы покупателей → Бизнес-процессы`
в тулбаре списка). Структура редактора:

- **Статусы для создания документов** — список статусов, в которых МОЖНО
  создать новый документ этого типа (по умолчанию только «Новый»), + кто
  именно может создавать в этом статусе (см. селектор ниже). Можно добавить
  несколько таких правил («+ Добавить ещё»).
- **Этапы бизнес-процесса** — список правил-переходов, каждое: **набор
  статусов-источников** (multi-select, не один статус) → **набор
  статусов-назначения** (multi-select) + **кто может выполнить переход**.
  Т.е. это не жёсткий линейный конечный автомат «один-статус-в-один-статус», а
  граф с множественными источниками/целями на правило.
- **Селектор «кто может»** (переиспользуется и для создания, и для каждого
  перехода) — модалка «Выбор сотрудников» с тумблером «Выбраны все сотрудники
  аккаунта» и, если выключить, тремя способами набрать список: **по
  отдельным сотрудникам** (с поиском), **по отделам** (чекбоксы), **по ролям**
  (Администратор/Владелец аккаунта/кастомные роли — чекбоксы). Это третье,
  не описанное в Блоке I измерение прав: **право не на просмотр/CRUD
  сущности, а на конкретный переход статуса**, назначаемое по
  сотруднику/отделу/роли одновременно.

**Update 2026-08-29 — уже частично было и теперь доведено до паритета**:
проверка кода показала, что граф переходов у нас **уже существовал**
(`DocumentStatusTransition`, C4 follow-up) — вывод выше был неточным,
написан до сверки с кодом. Реально не хватало только одного измерения:
`allowedRoles` ограничивал переход лишь базовым enum `Role`, без
`CustomRole`/конкретного сотрудника. Закрыто в этом же заходе: добавлены
`allowedCustomRoleIds`/`allowedEmployeeIds` (OR между всеми тремя — как в
МойСклад), проведено через схему/`lib/document-statuses.ts`/обе actions
(`orders.ts`, `purchase-orders.ts`)/UI (`document-status-transitions-manager.
tsx` — чекбоксы по ролям, кастомным ролям и сотрудникам, колонка «Кому
разрешено»). Проверено вживую (`db push`, typecheck, eslint, ручной прогон в
тестовом аккаунте): сотруднику без нужной кастомной роли статус-цель физически
не появляется в выпадающем списке — 403-эквивалент на уровне выбора, не
только на сохранении.

### 2. Сценарии — event → condition → action автоматизация

`Моя компания → Сценарии` (7 включённых по умолчанию: уведомления на создание
счёта/отгрузки/заказа поставщику/приёмки/производственного задания, на оплату
счёта, на просрочку заказа поставщику — все **сценарии-уведомления**,
не бизнес-логика). Конструктор нового сценария:

- **Событие**: Объект (~30 типов документов, сгруппированных по тем же 8
  вкладкам, что и матрица прав: Закупки/Продажи/Товары/CRM/Склад/Деньги/
  Розница/Производство) × Событие (всего два: **Создан** / **Изменен** —
  специфичных «статус изменён на X» события нет, это выражается через
  условия ниже).
- **Действия** (можно добавить несколько, цепочкой): Изменить заказ (сам
  документ-источник), Изменить контрагента, Изменить резерв, Создать задачу,
  Отправить уведомление, Отправить вебхук (внешняя интеграция), **Создать
  связанный документ** (автогенерация следующего документа в цепочке без
  участия человека), Добавить действие из «Решения» (маркетплейс
  плагинов, помечено «Новое»).
- **Когда выполнить**: сразу или отложенно («Через N дней/...») — то есть
  есть встроенный delay/scheduler для действий.
- **Условия**: «Добавить условие» + «Добавить группу условий» — деревянная
  структура условий с группировкой (судя по названию — И/ИЛИ группы), не
  плоский список.

Не наша ближайшая задача (это отдельный крупный блок, вроде E/F), но полезно
знать форму: событие+условия(дерево)+действия(цепочка)+задержка — стандартный
паттерн rule-engine, если когда-то будем делать автоматизации.

### 3. «Создать документ» — граф конвертации документов друг в друга

На карточке Заказа покупателя кнопка «Создать документ» показала полный
список того, во что заказ может быть напрямую конвертирован (с переносом
позиций/сумм/контрагента):

Перемещение, Счет покупателю, Волна отбора (склад-пикинг), Отгрузка, Входящий
платеж, Приходный ордер, Предоплата (задизейблено — видимо, нужна включённая
онлайн-оплата), **Заказ поставщику** и **Заказ поставщику (с учётом
«доступно»)** — прямая конвертация заказа покупателя в заказ поставщику,
причём второй вариант умеет вычесть то, что уже есть в наличии (докупить
только недостачу), Розничная продажа, Снабжение.

Также в шапке документа увидены отдельно от статуса: **чекбокс «Проведено»**
(проведение документа — влияет на остатки/деньги, отдельная сущность от
статуса «Новый»/etc, включена по умолчанию даже у черновика) и **чекбокс
«Резерв»** (резервирование товара под заказ, выключен по умолчанию), плюс
кнопка «Запросить оплату» (генерирует ссылку на оплату для контрагента) и
бейдж оплаты «Не оплачено» — то есть у документа минимум 3 независимых
измерения состояния одновременно: Статус (кастомизируемый), Проведено
(да/нет), Оплата (оплачено/не оплачено/частично, надо полагать). У нас в
`Order`, по всей видимости, это сейчас смешано в один enum статуса — стоит
учитывать при проектировании полноценного жизненного цикла заказа, что
эталон держит эти оси раздельно.

Реализация не начата — только исследование, зафиксировано для будущего
захода на жизненный цикл документов (сейчас у нас Block C — MVP-версия
документооборота, без статус-графа, без бизнес-процессов, без сценариев).

## Блок L — Система подписок и панель разработчика (по явному запросу 2026-08-30, не начато)

Запрошено пользователем: реализовать систему подписки (платные тарифы/лимиты
для организаций) и отдельную панель разработчика (супер-админка над всеми
организациями) — выдача/отзыв подписок, управление доступами, просмотр всех
открытых фич. Явно подчёркнуто: **кибербезопасность панели — приоритет №1**,
это самая чувствительная поверхность атаки во всём продукте (компрометация
даёт доступ ко всем организациям сразу, а не к одной, в отличие от любой
другой дыры в проекте).

### 1. Система подписок

- **Тарифы/планы** — новая модель `SubscriptionPlan` (название, лимиты: макс.
  сотрудников, макс. заказов/мес, доступные фичи как список флагов, цена,
  период). `Organization` получает `subscriptionId` → текущий активный тариф
  + `subscriptionExpiresAt`.
- **Лимиты/гейтинг фич** — точки проверки лимитов рядом с уже существующим
  `assertPermission` (Блок I), не вместо него: например, "план не позволяет
  больше N сотрудников" при создании `Membership`, "фича X недоступна на
  тарифе Free" на входе в соответствующий раздел UI.
- **Оплата** — нужно сначала решить, какой платёжный провайдер (ЮKassa/
  Stripe/др.) — архитектурный блокер, не начинать реализацию биллинга
  вслепую до этого решения.
- **История подписки** — журнал изменений (кто/когда выдал/продлил/отозвал),
  нужен и для панели разработчика (аудит), и для самой организации
  (прозрачность истории тарифа для клиента).

### 2. Панель разработчика (супер-админка)

Отдельный контур, **не часть** обычного `/[org]/...` дерева страниц с
организационным скоупом — это межорганизационный доступ, поэтому по
архитектуре должен быть максимально изолирован от остального приложения.

- **Доступ** — не через обычную `Role` организации, а отдельный флаг на
  `User` (например `isSuperAdmin`, или отдельная таблица `PlatformAdmin`),
  не связанный с `Membership`/`CustomRole`. Обычный ADMIN организации НЕ
  должен автоматически получать доступ к этой панели.
- **Функции**: список всех организаций (поиск/фильтр), выдача/изменение/
  отзыв подписки на организацию (с обязательным логом, кто из платформенных
  админов и когда это сделал), просмотр и точечное переключение фич/флагов
  организации для отладки/поддержки.
- **Сознательно не входит по умолчанию**: просмотр самих бизнес-данных
  клиента (заказы/клиенты/каталог конкретной организации) — понадобится для
  поддержки, но это отдельный, отдельно логируемый "impersonation"-режим,
  не тихий доступ мимо аудита.

### 3. Кибербезопасность — явный приоритет, не общий чек-лист "для галочки"

Пользователь отдельно подчеркнул это как главное в блоке. Пункты ниже
закрываются **до** деплоя панели, не после:

- **Изоляция маршрута** — `/admin` (или похожий префикс) недостижим без
  проверки `isSuperAdmin` на каждом server action и в middleware/layout, а
  не только скрытый пункт меню (security through obscurity — не защита).
- **MFA для платформенных админов** — обычного пароля недостаточно для
  аккаунта, способного выдавать/отзывать доступ у всех клиентов сразу; решить,
  добавлять ли TOTP-провайдер поверх next-auth именно для этой роли (не
  обязательно для всех пользователей продукта).
- **Аудит-лог** — каждое действие в панели (выдача подписки, включение фичи,
  просмотр организации) пишется в append-only лог (админ/время/до/после) —
  не переиспользовать существующий Webhook-лог, это другая по чувствительности
  сущность.
- **Rate limiting / брутфорс-защита** — на логин в панель отдельно от обычного
  логина организации: цель атаки здесь ценнее (доступ ко всем тенантам сразу).
- **Отдельная сессия от пользовательской** — если платформенный админ также
  ADMIN своей организации, компрометация одной сессии не должна автоматически
  означать доступ к панели разработчика.
- **Секреты платёжного провайдера** — ключи API только в `.env`/секрет-
  хранилище, никогда не в код и не в `NEXT_PUBLIC_*` (утечёт на клиент).
- **Принцип наименьших привилегий** — если платформенных админов несколько,
  разделить на уровни (например "видит подписки" vs "может отозвать
  подписку"), не единственная суперроль без явного запроса на обратное.

**Не начинать одним гигантским заходом** — сначала нужно решить платёжного
провайдера (блокер для подписок) и модель доступа платформенных админов
(блокер для панели), оба решения архитектурные, не чисто технические —
разумно обсудить отдельно перед началом кода, как и с Блоком I.

## Блок M — Доводка систем со сознательным упрощением до уровня МойСклад (план, не начато, по явному запросу 2026-08-31)

Каждый пункт — доработка уже реализованной и рабочей функциональности, не
баг. Список ниже — единственное место, где эти доработки спланированы;
детали текущего упрощения — в разделе соответствующего блока (ссылки в
скобках). Не начинать пункт без явного запроса — каждый меняет проверенное
ядро (леджер/отчёты), а не периферию.

- ⬜ **M1. P&L — партионный учёт себестоимости** (см. Блок G). Сейчас:
  себестоимость = все `SUPPLY`-приёмки за период по закупочной цене, не
  привязано к конкретной проданной единице. План: новая модель `StockBatch`
  (одна на приёмку `SUPPLY` — остаток, цена) + опциональный `batchId` на
  `StockMovementLine` у `DEMAND`; списание FIFO по батчам в
  `createDemand`; `getPnlReport` считает себестоимость по факту списанных
  батчей. Старые движения без `batchId` — fallback на текущую логику
  (обратная совместимость, без ретроактивной разбивки истории). Сложность:
  средняя-высокая, трогает ядро склада (`createDemand`).
- ⬜ **M2. Мультивалютность — курс на дату операции** (см. H2). Сейчас:
  `toBase()` всегда берёт последний известный курс. План: `rateSnapshot`
  (Decimal?) на `Payment`/`StockMovementLine`, снимается один раз в момент
  проведения операции (`effectiveAt <= дата операции`, последний такой
  курс); отчёты используют snapshot, если есть, иначе — текущий fallback.
  Сложность: низкая-средняя, локально в паре write-путей + отчётах.
- ⬜ **M3. Вебхуки — очередь повторов** (см. H4). Сейчас: одна попытка,
  без ретрая (в проекте нет фоновой инфраструктуры вообще). План:
  `nextRetryAt`+`attemptCount` на `WebhookDelivery`, экспоненциальный
  backoff, лёгкий cron-эндпоинт (`/api/cron/webhook-retries`), вызываемый
  планировщиком хостинга по расписанию. Зависит от выбора деплой-платформы
  (см. Блок L — ещё не решено). Сложность: средняя.
- ⬜ **M4. Печать — серверный PDF** (см. H1). Сейчас: HTML +
  браузерная печать. План (если понадобится): API-роут
  `/api/print/orders/[id]/pdf` через headless-браузер (`playwright`/
  `puppeteer`) или `@react-pdf/renderer`, нужен только для автоматической
  рассылки/скачивания без диалога браузера — не начинать просто ради
  «красивее», добавляет тяжёлую рантайм-зависимость. Сложность: средняя.
- ⬜ **M5. Платежи — полноценные InvoiceIn/InvoiceOut/Prepayment** (см.
  C3). Сейчас: `Payment` (IN/OUT) + `getClientBalance`, без документов
  счетов. План: новые модели по паттерну `Order`/`PurchaseOrder`
  (LineItem + `DocumentStatus`), `Payment` получает опциональную привязку к
  Invoice. Сложность: высокая — по объёму сопоставимо с Блоком C2, по сути
  новый документооборот.
- ⬜ **M6. Остатки по модификациям товара** (см. A3). Сейчас: остаток
  считается только на уровне `CatalogItem`, `CatalogItemVariant` есть, но
  склад его не различает. План: `variantId` (опционально) на
  `StockMovementLine`, `getStockBalances` группирует по
  `(catalogItemId, variantId)`. Сложность: высокая, широкий блаcт-радиус —
  весь `StockMovement`-леджер (продажи/закупки/производство/перемещения/
  списания/возвраты).

## Принцип работы с этим роадмапом

1. MVP (Фазы 0–8) доводим до конца в любом случае — это база, без которой
   остальное не на чем строить (авторизация, роли, архивирование, паттерны
   UI).
2. Дальше — Блоки A → B → C → D в этом порядке: они прямо зависят друг от
   друга (нет смысла в документообороте продаж без складов, нет смысла в
   складах без нормального каталога).
3. Блок E — только по явному запросу пользователя или после того как
   найдутся клиенты, которым это нужно ("изучать боли клиентов"). Блок F
   (производство) реализован по такому явному запросу 2026-08-30, см. выше.
3a. Блок I (гибкие права/личный кабинет) — та же логика, что и E: ждёт
   явного запроса, это premium-фича даже у эталона.
4. Отчёты (G) и сквозные штуки (H) — вкрапляются по ходу, не ждут отдельного
   "часа X".
